# ADR-0457 2要素のリセットは確認の語と理由を求め、自分自身と一般の利用者を断る

> 状態: 推定 | 確認日: 2026-10-24 | 対象: `src/app/api/admin/users/mfa/reset/route.ts` | 基準コミット: `4facf63b`

## 概要

店長が店長・サポーターの2要素の登録を全部消す窓口は、確認の語 `RESET_MFA` と 10〜500 字の理由を求める。自分自身のリセットと、店長・サポーターでない利用者のリセットは断り、どの結果も監査に残す（中身は結果ごとに違う）。

## 判断

### ADR-0457 2要素のリセットは確認の語と理由を求め、自分自身と一般の利用者を断る

| 属性 | 値 |
| --- | --- |
| 上位 | DRV-ADMIN-002 |
| 根拠 | 2要素を消すと、その特権の利用者はパスワードだけで入り直して登録し直せる。取り返しがつかないので、確認の語で取り違えを防ぎ、理由を監査に残して後で確かめられるようにする。自分自身を断るのは、乗っ取った人が自分の2要素を外して居座るのを防ぐため。一般の利用者には2要素が無いので対象にしない（推定。判断の記録は無い） |
| 状態 | 推定 |
| 出どころ | 実装から推定（`src/app/api/admin/users/mfa/reset/route.ts`）、git `bbfb6143`（2026-05-10「Add security best practices and MFA management endpoints」） |

#### 背景

- 店長とサポーターはログインで2要素を求められる（FR-LOGIN-007、範囲外）。認証のアプリを失くすと管理画面に入れない
- 2要素の一覧と削除は Supabase の管理の機能で、service role でしか呼べない（ADR-0451）

#### 決定

- 本文は利用者の id（UUID）、前後の空白を除いて 10〜500 字の理由、確認の語 `RESET_MFA` だけを受ける（`mfa/reset/route.ts`）
- 自分自身は 400、利用者が無ければ 404、対象の役割が店長・サポーターでなければ 400
- 対象の役割は Auth の利用者の付帯の情報（`app_metadata`）の役割で決める
- 2要素の登録を全部消し、1つでも消せなければ 500
- どの結果も送り元の IP とブラウザの情報付きで監査に残す。中身は結果ごとに違う: 形の誤りは控えた利用者の id だけ、自分自身は付帯の情報なし、対象なしは理由、特権でないは理由と対象の役割、一覧の誤りは理由と誤りの文、消せない時は理由・全部の数・誤りの一覧、成功は理由・対象の役割・対象のメール・消した数

#### 退けた案

| 案 | 退けた理由 |
| --- | --- |
| 確認の語と理由を求めない | 取り違えた id で特権の利用者の2要素を消しても、後から理由を確かめられない（推定） |
| 自分自身のリセットも許す | 乗っ取った人が自分の2要素を外せる（推定） |
| 対象の役割を DB の ACL で決める | 今のコードは選んでいない。`hybrid-rbac.md` は重要な操作では ACL を見るとし、SEC-ADMIN-014 も ACL を求める（TM-ADMIN-11） |

#### 結果

- 良くなること: 誤った操作を減らし、誰が何の理由で消したかを監査で追える
- 悪くなること: リセットの後も対象の session を失効させない（`api-spec.md` は失効させると書く。TM-ADMIN-10。SEC-ADMIN-014 を参照）。監査に理由の文と対象のメールが平文で残る（SEC-ADMIN-008）。店長が別の店長の2要素も消せる
- 見直す条件: 2要素のリセットの画面を作る時（今は呼ぶ画面が無い）、SEC-ADMIN-014 に届く直しをする時
