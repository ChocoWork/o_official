# ADR-0353 最終改定日は固定の基準日と追跡の切り替え日（日本時間）の遅いほうにする

> 状態: 推定 | 確認日: 2026-10-26 | 対象: `src/app/privacy/page.tsx`・`src/app/privacy/revision-date.ts` | 基準コミット: `16df4479`

## 概要

`/privacy` の「最終改定日」を、固定の基準日（2026年10月26日。当初は 2026年7月11日で、2026-10-26 に上げた）と、追跡の設定が変わった時刻（日本時間の日付）の遅いほうにする。追跡を切り替えていない間は基準日のまま。

## 判断

### ADR-0353 最終改定日は固定の基準日と追跡の切り替え日（日本時間）の遅いほうにする

| 属性 | 値 |
| --- | --- |
| 上位 | SEC-PRIVACY-012 |
| 根拠 | 追跡の切り替えで委託の一覧の一文が出入りするのに、最終改定日が固定のままだと、方針が変わった日を本人が知れない（11 節は「掲載した時点から効力を生じる」と書く）。設定の更新時刻は既に DB が持つので、新しい列や設定は足さずにそれを使う |
| 状態 | 推定 |
| 出どころ | `.superpowers/sdd/2026-10-25-security-gap-fixes/wave1c-decisions.md`（R18） |

#### 背景

- 頁は最終改定日を固定の字で持っていた。追跡をオンにして一文が増えても日付は変わらなかった
- 設定の関数は更新時刻（`updatedAt`）を返すが、頁は使っていなかった

#### 決定

- 最終改定日 = 基準日 `2026-10-26` と、設定の更新時刻を日本時間の日付にした物の、遅いほう。「YYYY年M月D日」で出す（`resolveRevisionDate`）
- 更新時刻が null・読めない値・基準日より前の時は基準日
- 日本時間の日付で比べる。UTC の日付のままだと、日本時間の日付の変わり目（UTC の 15 時）で 1 日ずれる

#### 基準日の改定履歴

| 日付 | 基準日 | 理由 |
| --- | --- | --- |
| 2026-10-25 | `2026-07-11` | 頁に固定されていた日付（b82f3450、2026-07-12 追加）を、出発点の基準日としてそのまま引き継いだ |
| 2026-10-26 | `2026-10-26` | ユーザー判断（2026-10-26）。同日にポリシーの本文を変えたので、追跡を切り替えていない間も最終改定日が今日になるよう基準日を上げた。`PRIVACY_POLICY_BASE_REVISION` と、日付を固定したテスト（境目は日本時間 10月26日 0 時 = UTC 2026-10-25T15:00:00Z）を合わせて直した |

#### 退けた案

| 案 | 退けた理由 |
| --- | --- |
| 日付を固定の字のままにし、切り替えのたびに手で直す | 直し忘れで、変わった日を示せない。公表の中身と日付がずれる |
| 基準日を持たず、更新時刻だけにする | 一度も切り替えていない間（`updatedAt` が null）の日付が決まらない |
| 方針の変更の履歴を別の表に持つ | 決定にない。設定の更新時刻で足りる |

#### 結果

- 良くなること: 追跡を切り替えた日が最終改定日に出る。新しい列・設定は要らない
- 悪くなること: 頁が `updatedAt` を使う。SEC-PRIVACY-002 の「受け取る欄」に更新時刻が加わった（担当者のメールと件数は受け取らない）
- 悪くなること: オンからオフに戻した時も、戻した日が最終改定日になる。それでよいかは確かめていない
- 見直す条件: 委託の一覧を設定以外の理由で変える時（その時は基準日を直す）
