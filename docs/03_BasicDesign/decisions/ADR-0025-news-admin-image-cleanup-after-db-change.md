# ADR-0025 管理のニュースの画像は、DB の変更の後に置き場から消し、失敗は記録だけにする

> 状態: 現行 | 確認日: 2026-10-26 | 対象: `src/features/news/services/admin-images.ts`、`src/app/api/admin/news/route.ts`、`src/app/api/admin/news/[id]/route.ts`、`src/components/NewsSection.tsx`、`src/app/admin/news/edit/[id]/page.tsx` | 基準コミット: `16df4479`（作業ツリーに別の作業の未コミットの差分あり）

## 概要

管理のニュースの作成・更新・削除は、置き場 `news-images` に残る画像を、DB の行を変えた後に消す。消す前に道筋を1本ずつ「自分の置き場の `news/` の下の安全な文字だけ」で確かめ、置き場の削除の失敗は記録と監査の結果（`imageCleanup`）に残すだけで、応答は変えない。あわせて、画像は中身の先頭の印で種類を確かめ、保存名は送られた名前から作らない。PUT は画像を上げる前にその記事の古い `image_url` を読み、無い記事には何も上げない。1件の取り出しは「無い」（404）と「DB の失敗」（500）を分け、管理の一覧は取得の失敗を「記事が無い」と別に見せる。

## 判断

### ADR-0025 管理のニュースの画像は、DB の変更の後に置き場から消し、失敗は記録だけにする

| 属性 | 値 |
| --- | --- |
| 上位 | SEC-NEWS-017、SEC-NEWS-018 |
| 根拠 | 消したはずの画像を置き場に残さず、容量をためないため（THR-NEWS-017）。置き場は service role で書くので、申告の種類と送られたファイル名を信じない（THR-NEWS-016）。置き場の削除を先にすると、行の更新が失敗した時に行が消えた画像を指してしまうので、順は「行 → 置き場」にする |
| 状態 | 現行 |
| 出どころ | `design-final.md` の R12・R14（波 1-C の計画。ユーザーが「波1を全部（推奨）」と承認した 2026-10-26） |

#### 背景

- 削除は記事の行だけを消し、更新は古い画像を、作成の保存の失敗は上げ終えた画像を、置き場に残していた
- PUT は画像を先に上げてから更新したので、無い id の PUT（0 行で 404）でも、上げた画像が置き場に残った
- 画像の種類は申告の `File.type` だけを見て、PUT の拡張子は送られたファイル名から取っていた
- 1件の取り出しは `.single()` で、行が無い時も DB の失敗の時も 404 だった。管理の一覧は取得の失敗を「ニュース記事がありません」と同じに見せた。編集のページは URL の id を確かめずに窓口の道へ入れた

#### 決定

- 中身の確かめ: `prepareNewsImage` が先頭の印（JPEG・PNG・GIF・WebP）を読み、申告と同じ時だけ通す。確かめは種類と大きさの確かめの直後・置き場に書く前に済ませる。保存名は `news/<UTC の日付>/<uuid>.<検出した種類の拡張子>`（POST・PUT とも）
- 順: 行を先に変える → 置き場を消す。作成は DB の保存が失敗・例外になった時に上げた画像を消す。更新は行の更新が成功した後に古い画像を消し、更新が失敗・0 行・例外になった時は **その要求で上げた新しい画像** を消す（古い画像は消さない）。削除は `delete().select('id, image_url')` で消した行の `image_url` を受け取り、行を消した後に消す
- PUT の古い値: 画像を付けた時は、上げる前に利用者の session の client で `select('image_url').eq('id', id).maybeSingle()` を読む。記事が無ければ 404 で何も上げず、読みの失敗は 500 で何も上げない
- 確かめ: 消す道筋は1本ずつ `isOwnNewsImagePath`（`/^news\/[A-Za-z0-9][A-Za-z0-9._-]*(\/[A-Za-z0-9][A-Za-z0-9._-]*)*$/`）を通す。`..`・先頭の `/`・別の置き場・外の URL・古い見本の道筋（`e2e/news-1.png` など。接頭辞が違う）は渡さない（消さない側に倒れる）。同じ道筋が新旧に残る時は消さない。値は共有の `extractNewsImageObjectPath` で道筋に直す（呼ぶだけ）
- 置き場の削除は service role の client で行う。利用者の session の client で消すと、置き場の方針（`storage.objects` の RLS）次第で断られ、方針を足す移行が要る。DELETE は利用者の session の client しか作らないので、行を消した後にだけ `createServiceRoleClient()` を作って消すのに使う（行の削除・存在の判定には使わない）。client を作れない時も例外にせず `failed` とする
- 失敗: 置き場の削除の失敗は、名前と符号だけを記録し、監査の `metadata.imageCleanup`（`ok`・`failed`）に残すだけ。応答は変えない（行はもう変わっている）
- 取り出し: `GET /api/admin/news/[id]` は `isNewsId` を通らない id では DB を呼ばず 404、`.maybeSingle()` で行が無い時だけ 404、DB の失敗は固定の文 `Failed to fetch news article` の 500。管理の一覧（`NewsSection`）は取得の失敗に `role="alert"` の「ニュース記事の取得に失敗しました」と「再読み込み」のボタンを出し、「ニュース記事がありません」と分ける。編集のページは `isNewsId` を通らない id では要求を送らず「記事の読み込みに失敗しました」を出し、通った id も `encodeURIComponent` を通す
- id の確かめ: 窓口の `[id]` の旧 `/^\d{1,18}$/` を、公開と同じ `isNewsId`（`/^[1-9]\d{0,17}$/`）に統一した。`0`・`007` を DB に渡さず 404 にする
- 記録: 触るファイルの `console.error` は `describeErrorForLog`（名前と符号だけ）にする

#### Shopify との突き合わせ

| 観点 | Shopify の一般的な形 | この判断 |
| --- | --- | --- |
| アップロードの種類の確かめ | ファイルの中身を見て受け付け、保存先の名前は Shopify 側が決める（出典は未確認） | 中身の先頭の印を見て、保存名は日付と乱数だけで作る |
| 記事を消した時の画像 | 記事に付いたメディアは記事と一緒に消える（出典は未確認） | 行を消した後に置き場の画像も消す |
| 後始末の失敗 | 消し残しは運用側の掃除に任せ、操作は成功にする（出典は未確認） | 応答は成功のまま、記録と監査に結果を残す |
| 管理の一覧の障害 | 読み込みの失敗は「0 件」でなくエラーの表示と再試行を出す（出典は未確認） | 失敗の知らせと「再読み込み」を出す |

#### 退けた案

| 案 | 退けた理由 |
| --- | --- |
| 置き場を先に消してから行を変える | 行の更新が失敗すると、行が消えた画像を指したまま残る |
| 置き場の削除の失敗で応答を失敗にする | 行はもう変わっているので、利用者に失敗と見せると二重の操作を招く |
| 行の `image_url` をそのまま消す | 古い見本の道筋や外の URL まで service role で消す側に倒れる |
| 利用者の session の client で消す | 置き場の方針次第で断られ、移行が要る。波 1-C は移行を作らない |
| PUT の存在確認を画像の後にする | 無い id でも置き場に孤児が出る。確認を上げる前に置くほうが簡単で確実 |
| 署名の共有ライブラリの確かめに今すぐ差し替える | 共有部品は波 3 の範囲。それまでは領域の中の確かめを使う |

#### 結果

- 良くなること: 消した・差し替えた・失敗した画像が置き場に残らない。偽の画像や区切りを含む名前が置き場に入らない。置き場の誤りの文が応答や記録に出ない。管理者が障害を「記事が無い」と取り違えない。編集のページが別の窓口へ要求を送らない
- 悪くなること: 置き場の削除の失敗で消し残しが出うる（結果は監査に残る）。古い見本の道筋の画像は消えない。画像つきの PUT は古い値を読む分だけ DB の往復が 1 回増える
- 残る弱さ: PUT は「古い値を読む → 上げる → 行を変える → 古い画像を消す」が 1 つのまとまりでない。同じ記事に PUT が同時に 2 本来ると、先に終えた方が上げた画像が行から外れて置き場に残りうる。本番に既に残っている孤児の画像の掃除は別の運用作業
- 見直す条件: 署名の共有ライブラリが共有の道筋の確かめを持った時（その関数に差し替える）、消し残しが増えた時（定期の掃除を足す）
