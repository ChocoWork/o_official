# ADR-0160 管理の LOOK の画像は、行を変えた後に置き場から消し、失敗は記録だけにする

> 状態: 現行 | 確認日: 2026-10-26 | 対象: `src/features/look/services/admin-images.ts`、`src/app/api/admin/looks/route.ts`、`src/app/api/admin/looks/[id]/route.ts` | 基準コミット: `4fe88539`（作業ツリーに別の作業の未コミットの差分あり）

## 概要

管理の LOOK の作成・更新・削除は、置き場 `look-images` に残る画像を、DB の行を変えた後に消す。消す前に道筋を1本ずつ「自分の置き場の `looks/` の下の安全な文字だけ」で確かめ、置き場の削除の失敗は記録と監査の件数に残すだけで、応答は変えない。あわせて、画像は中身の先頭の印で種類を確かめ、保存名は送られた名前から作らない。

## 判断

### ADR-0160 管理の LOOK の画像は、行を変えた後に置き場から消し、失敗は記録だけにする

| 属性 | 値 |
| --- | --- |
| 上位 | SEC-LOOK-013、SEC-LOOK-014、SEC-LOOK-021 |
| 根拠 | 消したはずの画像を置き場に残さず、容量をためないため（THR-LOOK-014）。置き場は service role で書くので、申告の種類と送られたファイル名を信じない（THR-LOOK-013）。置き場の削除を先にすると、行の更新が失敗した時に行が消えた画像を指してしまうので、順は「行 → 置き場」にする |
| 状態 | 現行 |
| 出どころ | `design-final.md` の R14（波 1-C の計画。ユーザーが「波1を全部（推奨）」と承認した 2026-10-26） |

#### 背景

- 削除は LOOK の行だけを消し、更新は古い画像を、作成と更新の途中の失敗は上げ終えた画像を、置き場に残していた
- 画像の種類は申告の `File.type` だけを見て、拡張子は送られたファイル名から取っていた。置き場の誤りの文を応答に出していた

#### 決定

- 中身の確かめ: `prepareLookImage` が先頭の印（JPEG・PNG・GIF・WebP）を読み、申告と同じ時だけ通す。確かめは大きさの確かめの直後・1時間の量の枠の前・置き場に書く前に済ませる（偽の画像で枠を使わせない）。保存名は `looks/<UTC の日付>/<uuid>.<検出した種類の拡張子>`
- 順: 行を先に変える → 置き場を消す。作成は途中の失敗で上げ終えた画像を消す。更新は行の更新が成功した後に古い画像を消し、更新が失敗したら **その要求で上げた新しい画像** を消す。行が新しい道筋を指した後に関連の保存が失敗した時は、新しい画像を残し古い画像を消す。削除は存在確認で `image_urls` を行を消す前に読み、行の削除が成功した後に消す
- 確かめ: 消す道筋は1本ずつ `isOwnLookImagePath`（`/^looks\/[A-Za-z0-9][A-Za-z0-9._-]*(\/[A-Za-z0-9][A-Za-z0-9._-]*)*$/`）を通す。`..`・先頭の `/`・別の置き場・外の URL・古い見本の道筋（`e2e/look-1-1.png` など。接頭辞が違う）は渡さない（消さない側に倒れる）。同じ道筋が新旧に残る時は消さない
- 置き場の削除は、上げるのと同じ service role の client で行う。利用者の session の client で消すと、置き場の方針（`storage.objects` の RLS）次第で断られ、移行が要る
- 失敗: 置き場の削除の失敗は、名前と符号だけを記録し、監査の `metadata`（`image_cleanup:'failed'`・`orphaned_count`）に件数を残すだけ。応答は変えない（行はもう変わっている）
- 記録: 触るファイルの `console.error` は `describeErrorForLog`（名前と符号だけ）にする。アップロードの失敗の応答は `Failed to upload image` ちょうど

#### Shopify との突き合わせ

| 観点 | Shopify の一般的な形 | この判断 |
| --- | --- | --- |
| アップロードの種類の確かめ | ファイルの中身を見て受け付け、保存先の名前は店が付ける物でなく Shopify 側が決める（出典は未確認） | 中身の先頭の印を見て、保存名は日付と乱数だけで作る |
| 商品を消した時の画像 | 商品に付いたメディアは商品と一緒に消える（出典は未確認） | 行を消した後に置き場の画像も消す |
| 後始末の失敗 | 消し残しは運用側の掃除に任せ、操作は成功にする（出典は未確認） | 応答は成功のまま、記録と監査に件数を残す |

#### 退けた案

| 案 | 退けた理由 |
| --- | --- |
| 置き場を先に消してから行を変える | 行の更新が失敗すると、行が消えた画像を指したまま残る |
| 置き場の削除の失敗で応答を失敗にする | 行はもう変わっているので、利用者に失敗と見せると二重の操作を招く |
| 行の `image_urls` をそのまま全部消す | 古い見本の道筋や外の URL まで service role で消す側に倒れる |
| 利用者の session の client で消す | 置き場の方針次第で断られ、移行が要る。波 1-C は移行を作らない |
| 署名の共有ライブラリの確かめに今すぐ差し替える | 共有部品は波 3 の範囲。それまでは領域の中の確かめを使う |

#### 結果

- 良くなること: 消した・差し替えた・失敗した画像が置き場に残らない。偽の画像や区切りを含む名前が置き場に入らない。置き場の誤りの文が応答や記録に出ない
- 悪くなること: 置き場の削除の失敗で消し残しが出うる（件数は監査に残る）。古い見本の道筋の画像は消えない。DELETE と PUT の存在確認が `image_urls` を読む分だけ、読む列が増える
- 残る弱さ（波 2）: PUT は「古い `image_urls` を読む → 上げる → 行を変える → 古い画像を消す」が 1 つのまとまりでない。同じ LOOK に PUT が同時に 2 本来ると、先に終えた方が上げた新しい画像が、後の更新で行から外れて置き場に残りうる。SEC-LOOK-015（更新の DB の関数化、波 2）で直す
- 作成で `look_items` の保存が失敗し、続く `looks` の行の削除も失敗した時は、行が残るので画像は消さない（`metadata.row_cleanup:'failed'`）
- 見直す条件: 署名の共有ライブラリが共有の道筋の確かめを持った時（その関数に差し替える）、消し残しが増えた時（定期の掃除を足す）
