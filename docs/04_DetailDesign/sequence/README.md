# シーケンス設計の案内と記載方針

> 状態: 現行ソースとの同期方針 | 確認日: 2026-10-04 | 対象: 認証・購入・注文管理の実行時相互作用

## 概要

シーケンス図は、ある操作を開始してから結果が返るまでの参加者間の順序を示す。このディレクトリでは、既存の認証設計と注文・決済設計が扱っていた領域を、現行の Route Handler、サービス、RPC、呼び出し元に照合して記録する。全APIの一覧は[API設計](../../03_BasicDesign/api/api-spec.md)、画面間の移動は[画面遷移](../../03_BasicDesign/ui/screen-flow.md)を参照する。

## 分割と粒度の決定

| 単位 | 採用するルール | 理由・分割条件 |
| --- | --- | --- |
| ファイル | 認証方式、購入受付、Webhook処理、管理操作などの機能単位 | 同じ目的・実装境界を保守する。参加者や開始契機が大きく違う機能は別ファイルにする |
| 1つの図 | 1つのユースケース、または明示した部分シナリオ | 開始契機・事前条件・終了結果を図の前に示す。別の操作や別の非同期起動に移ったら図を分ける |
| 参加者 | 利用者、ブラウザ、API、認証サービス、DB/RPC、外部決済等の実際の境界 | 内部の全関数をライフラインにしない。順序・認可・永続化・冪等性を理解するために必要な境界を使う |
| メッセージ | 実際のHTTPパス、SDK操作、重要なRPCと結果 | フィールドの全定義や全SQLは図に複写せず、根拠表と関連設計にリンクする |
| 代替・例外 | 同じ開始契機の分岐は `alt`・`opt`、途中終了は `break`、細かい応答は補足表 | 成功と失敗の時系列を隠さない。再送、再試行、競合、部分成功を区別する |
| 非同期処理 | Webhook受付とworker実行を別図にする | 受付の200は注文処理完了を表さない。メッセージの順序や同時実行を実装で確認した範囲に限定する |

全機能を1枚に統合すると、登録・ログイン・再設定やWebhookの別々の開始契機が連続した処理に見える。一方、APIごと・関数ごとの機械的な分割では、利用者の目的と永続化の境界が追いにくい。このため「機能別ファイル、シナリオ別の図」を採用する。図の枚数、参加者数、メッセージ数に世界共通の固定値があるとは扱わない。

## 共通フォーマットと根拠の扱い

各文書は「概要 → 範囲と根拠 → シナリオごとの事前条件・図・結果 → 例外と永続化 → 関連テスト → 未確認事項」で記述する。図に付ける `SQ-*` は図の参照IDであり、既存の要件IDの代わりではない。対応要件は既存のページ別設計・要求表へリンクする。

実線は呼び出し、破線は戻り値・応答として用いる。非同期性は線種だけから推測せず、メール送信や独立したCron起動を明記する。外部サービス内部のSQL、設定、実データはソースで見えないため描かない。SDKを呼んでいることと、外部サービスが実環境で成功したことを区別する。テストへのリンクは検証観点の参照であり、今回の実行成功証跡ではない。

## 採用した一次資料

- [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1)：相互作用と状態機械を別のモデルとして扱う記法の基準。Mermaidを用いた本書は、UML全体への形式的な準拠宣言ではない。
- [C4 Dynamic diagram](https://c4model.com/diagrams/dynamic)：特定の機能・ユースケースの実行時相互作用を示し、複雑な連携を選んで記述する。
- [arc42 Runtime view](https://docs.arc42.org/section-6/)と[詳細なシナリオの注意点](https://docs.arc42.org/tips/6-4/)：重要なユースケース、外部連携、例外の代表的なシナリオを選び、不要なコード詳細で可読性を失わない。
- [Mermaid sequenceDiagram](https://mermaid.js.org/syntax/sequenceDiagram.html)：リポジトリで使用するテキスト図の記法。インストール済みのMermaidで構文・描画を確認する。
