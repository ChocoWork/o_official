# グループ G-2 在庫一覧表・発注・数量確定・受け取り・原本添付 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 全商品の在庫一覧表を作り、発注（入力→確認→確定）・数量確定・「残りを打ち切る」・複数回の受け取り（FIFO接続）・見積/請求書の原本添付を提供し、既存の管理在庫窓口を `admin.stock.read` / `admin.stock.manage` へ切り替える。

**Architecture:** 在庫の正はG-1の追記台帳・割当・共通advisoryのままにし、発注書の9表を追加する。書込みはすべて非公開のDEFINER関数＋service_role専用の公開INVOKER委譲で、先頭に共通advisoryを取り、受け取りは同じ取引で良品入庫（`restock`）→FIFO→状態履歴→発注書の納品累計まで確定する。原本はブラウザから署名つき送り先へ直接置き、サーバーが読戻して検証してからDBへ確定する二段階にする。

**Tech Stack:** 現行の Next.js `^16.3.6`、React `^19.0.0`、TypeScript `^5`、Supabase Postgres 17・Storage、Zod `^4.3.6`、`pg`、`tsx`、Jest、React Testing Library、Playwright。依存を増やさない。

**Spec:** [承認済みG設計](../specs/2026-10-23-group-g-design.md)の2章（画面表）・4章（4-1〜4-4）・7-3・8章（G-2の表と窓口）・9章・10章・13章（FREQ-525〜530・540、FR-ADMIN-111・113〜115・119・123）・14章G-2行。基盤は[G-1計画](2026-10-24-group-g1-allocation.md)と本番適用済みの `20261023211425_group_g1_allocation.sql`（台帳は `.superpowers/sdd/2026-10-24-group-g1-allocation/progress.md`）。形式はG-1計画に合わせる。G-3・G-4の範囲（荷作り表・発送票・出荷日・新注文一覧/詳細・CSV・割当入替UI）は作らない。

**決めたこと（ruling）**

- 範囲は設計14章のG-2行だけ（荷作り・発送票・出荷日・新注文一覧/詳細・CSV・入替UIは作らない）。**受取の取消・数量訂正は G-2 に含める**（controller裁定。4-4の「追記と相殺で行い、既に発送して戻せない在庫を無理に減らさない」、8-1の相殺元ID・二重相殺不可、9-2の `admin.receiving.manage`=受取取消/訂正による）。相殺の受取（負の行）を同じ受取表に追記して納品済み・未納を戻し、在庫は **G-1の在庫を減らす規則そのまま**（`admin_record_stock_movement` :1786-1823）で減らす＝空き在庫を先に使い、足りない分は支払い済みの割当を新しい注文から外す。外す点数は確認の数（`expectedReleaseQuantity`）で確かめ、理由を必須にし、割当イベントと状態履歴の理由は `stock_adjustment`。取り消す数が空き在庫と外せる割当の合計を超える時だけ断る。発送で消費された数量は割当に残らないので外れない（G-3まで発送の入口は無く、現時点で消費済みの数量は存在しない）（Task 7）。
- 移行は **2本**。`supabase/migrations/<ts1>_group_g2_purchasing_foundation.sql`（権限切替・G-1持ち越し・9表・非公開bucket・全ての読取関数。見込み 75〜90 KB）と `…<ts2>_group_g2_purchasing_writers.sql`（書込み関数9本・公開委譲・ロック helper・書き手一覧の置換。見込み 75〜95 KB）。理由は(1)本番は `npx supabase db push --linked` でファイルごとに1取引で当て、1ファイルを約100 KB以下に保つため、(2)foundation は書込み口を持たず単独で当てても業務が動かない／writers は常に foundation の後、というレビュー境界、(3)G-1の528 KBのように1本にしない。**どちらかが100,000バイトを超えたら、その Task の最後で止めて controller に報告し、controller が3本目に分けるか決める**（実装者が黙って分けない）。各ファイルは自身の末尾assert（G-1の `$g1_final_objects$` と表ACLの意味比較、PG17の `MAINTAIN` を含む）を持つ。
- **データを変える文は書かない**（清掃・補完・権限行の再投入なし）。本番の変更はスキーマと `storage.buckets` の1行のみ（Task 1 の公開関数11本の anon / authenticated 実行権の剥奪は、本番では既に無い権限を外す文なので結果は変わらない＝2026-10-24 に確認済み）。よって本番適用前のowner確認は不要（Task 11の読取で想定外の注文・在庫の増減が見えた時だけ止めて報告する）。
- 発注書の保存する段階は `ordered`（発注確定直後。数量は仮）と `quantity_confirmed` の2つ。`partially_received / received / closed` は保存せず、DB関数が納品・未納・打切りの有無から導出する。`draft` は画面上の入力途中で、DBに保存しない。数量確定は**発注書の全行を一度に**行う（訂正も全行を送り、変化した行だけ版に残す）。
- 数式（DBに1か所）: `発注数量` = 行の `confirmed_quantity`（未確定はNULL）、`納品済み` = `received_quantity`（受取行の合計と同じ）、`未納` = `outstanding_quantity` = `confirmed_quantity − received_quantity`（生成列。未確定はNULL）、`発注済み` = 数量確定済みの行の未納の合計、`注文数` = 品物状態 `in_production + ready` の数量、`発注必要数` = `max(0, 注文数 − 在庫 − 発注済み)`、`在庫` = G-1の `on_hand`（`F+A+H`）。
- 「発注確定」は `POST /api/admin/purchase-orders`（発注書を初めて保存する操作）で、設計8-3の `confirm` はこれに当たる（監査名 `admin.purchase_orders.confirm`）。「発注書確認」は画面だけの段で、サーバーは呼ばない。
- 原本の取り込みは**ブラウザ→署名つき送り先へ直接**（20 MiBの本文をNextの関数に通さない。`return-photo-client.ts` と同じ道）。サーバーは読戻して種類・大きさ・SHA-256を確かめてからDBへ確定する。期限切れの予約は**表示で要確認にするだけ**で、cron・自動削除・自動消去は作らない。
- 受け取りの入庫は台帳 `restock`（良品数）、備考 `発注 ${発注番号} の受け取り`。**この行の `allocation_operation_id` はNULL**（G-1の台帳整合trigger `group_g_stock_movement_consistency` は、タグ付きの行に一致する割当イベントを求める。通常の入荷は `admin_record_stock_movement` と同じく無タグで、タグが付くのはFIFOが書く `purchase` 行だけ）。受け取りの取消の減算は台帳 `adjustment`（負数、備考 `発注 ${発注番号} の受け取り取消`、同じく無タグ）。割当を外す時は G-1 と同じタグ付きの `allocation_release` と `release` イベント（理由 `stock_adjustment`）を書く。割当イベントの理由は既存の `fifo` を使い、**`ALLOCATION_EVENT_REASON_CODES` と台帳理由のCHECKは変えない**。状態履歴の理由は文字列 `purchase_order_receive`。
- 確定前の発注の取消（I2）: 段階が `ordered` の発注書は、**全行を渡した**打切りで取り消せる（確定数量を全行0にして段階を `quantity_confirmed` へ進め、打切りの履歴に仮数量を残す。表示は `closed`）。重複・誤入力の発注の最短の直し方を塞がないため。
- 読取も権限をDBで確かめる（I4）: G-2で作る4つの読取（`list_admin_inventory`・`list_admin_purchase_order_lines`・`get_admin_purchase_order`・`search_purchase_order_documents`）は最後の引数 `_actor_id uuid` を取り、`private.group_g_actor_has_permissions` で `admin.stock.read` または `admin.purchase_orders.read` を確かめて `GROUP_G_FORBIDDEN / 42501`。routeは `authz.userId` を渡す。G-1から続く既存の読取RPC（variantsのGETが使う `list_group_g_variant_inventory` など）は窓口だけで守り、変えない。
- 原本の一方失敗からの再開（I6）: 予約IDだけをブラウザが覚える（ページを読み直すと `File` と `sha256` は失われる）。再開は(1)`POST …/reservations/[reservationId]/upload-url` で置き場の有無を確かめる、(2)無ければファイルを選び直して `PUT`（ブラウザのSHA-256を送る＝`sha256_source='browser'`）、(3)既に置いてあれば取引日・金額・取引先を入れ直して確定し、**サーバーが読戻した本文のSHA-256を記録する（`sha256_source='server'`。ブラウザの値との照合はできないことを列で残す）**。
- 管理ナビ（I3）: `INVENTORY` タブは店長とサポーターの両方に出す（権限はON/OFFで役割ごとに変わるため）。各ページが自分の権限の文を出し、窓口とDBが守る。
- 変えなかった指摘（Minor。理由）: 5 `GET …/variants` が呼ぶ `backfill_item_variants`（色・サイズの同期の書込み）は、G-2前から読取の時に呼ぶ冪等な同期で、権限の外へ書込みを広げないので残す。7 期限切れの予約を「確認済み」にして消す追記表は作らない（YAGNI。運用文書とownerへの報告に「期限切れは残り続け、手で確認する」と書く）。11 Self-Reviewの restatement と各Taskの Docs の繰り返しは圧縮したが、受け取りの取消・確定前の取消・読取の権限・再開の経路を足したため全体は増えた（約150 KB）。値の表・エラー表・試験名は実装者が1通りに書くための値なので削らない。

## Global Constraints

- 実装はmaster。実装者はコミットせず、controllerがTaskのFilesだけを確認してコミットする。既存の `.claude/CLAUDE.md`・`package.json`・`.superpowers/` の差分を保持する。ブランチ/worktreeは作らない。**pushしない**。
- 移行は上の2本。ローカルCLIの `migration new --help` を確認し、実装時UTCの `<ts>` で作る（`<ts1>` はTask 1、`<ts2>` はTask 4。どちらも現在末尾 `20261023211425` より後）。適用済みSQLを変えず、UTF-8/BOMなし/LF。各ファイルの先頭は `BEGIN;`、末尾は最終assert→`NOTIFY pgrst, 'reload schema';`→`COMMIT;` を**1組だけ**。節の印は `-- G2A_BODY_BEGIN/END`・`-- G2A_FINAL_ASSERT_BEGIN/END`（writersは `G2B`）。
- 新しい本体関数はprivate schema、所有者postgres、`SECURITY DEFINER SET search_path = ''`、完全修飾名。公開RPCはservice_role専用の `LANGUAGE sql SECURITY INVOKER` 委譲（本体と同名・同引数・同戻り型）。各新objectのPUBLIC/anon/authenticatedは個別REVOKE、内部helperはservice_roleからもREVOKE。**`USAGE ON SCHEMA private` をREVOKE/GRANTする文は書かない**（`private.set_request_context()` の hook を保つ）。

- 追記専用: `purchase_order_revisions / short_closures / receipts / receipt_lines / attachment_reservations / attachments / attachment_revisions` の7表に `<表>_no_update`・`_no_delete`（BEFORE行）・`_no_truncate`（BEFORE文）を `private.reject_group_g_event_mutation()`（`GROUP_G_HISTORY_IMMUTABLE / 55000`）で付ける。`purchase_orders / purchase_order_lines` は DELETE・TRUNCATE を同関数で拒否し、UPDATEは Task 2 の守りだけで通す。
