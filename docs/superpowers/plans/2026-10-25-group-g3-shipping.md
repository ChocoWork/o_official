# グループ G-3 荷作り表・発送票・同梱・出荷日 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 荷作り表（発送準備中の品物だけ）から発送票を作り、同じお客様・同じ送り先の注文を同梱して一括で発送確定し、伝票番号の後入力・訂正、手動の配達済み、発送の取消、実際の出荷日とその訂正履歴を票単位で提供する。G-1 から止めている発送・発送取消・伝票訂正・手動の配達済みを、この新しい流れで再開する（旧4RPCは再開しない）。

**Architecture:** 在庫の正は G-1 の追記台帳・割当・共通 advisory（`190521,1`）のまま、発送票の6表を足す。書込みはすべて非公開の DEFINER 関数＋service_role 専用の公開 INVOKER 委譲で、先頭に共通 advisory を取る。発送確定は同じ取引で「注文ごとの `order_fulfillments`＋行 → 割当の `consume` → 状態履歴 → 注文ごとの outbox → 追跡の親」まで確定し、`consume` で裏付けのない発送行は遅延 constraint trigger が commit で断る。追跡の外部登録は票×版で1つの「代表の発送」の行だけが担い、結果は票の全注文へ広げる。

**Tech Stack:** 現行の Next.js `^16.3.6`、React `^19.0.0`、TypeScript `^5`、Supabase Postgres 17・PostgREST、Zod `^4.3.6`、`pg`、`tsx`、Jest、React Testing Library、Playwright。依存を増やさない。

**Spec:** [承認済みG設計](../specs/2026-10-23-group-g-design.md)の2章（画面表）・5章（5-1〜5-4）・6章（品物状態のうち G-3 が動かす遷移）・7章（7-1 の発送・発送取消の行、7-3 の全体ロック順と旧配送RPCの停止）・8章（G-3 の表と窓口）・9章（9-2 の `admin.shipping.*` 3コード、9-3）・11章（G-1 からの停止と G-3 での再開）・12章（メールと客向け画面）・13章（FREQ-531〜535・540〜541 の G-3 部分、FR-ADMIN-116・117・118・120・123、13-3 の停止ケースの処置）・14章 G-3 行。基盤は [G-1計画](2026-10-24-group-g1-allocation.md)・[G-2計画](2026-10-24-group-g2-purchasing.md)と本番適用済みの `20261023211425_group_g1_allocation.sql`・`20261024153505_group_g2_purchasing_foundation.sql`・`20261024180500_group_g2_purchasing_writers.sql`（台帳は `.superpowers/sdd/2026-10-24-group-g1-allocation/progress.md` と `…/2026-10-24-group-g2-purchasing/progress.md`）。追跡は [E-4 設計](../specs/2026-10-21-delivery-status-design.md)・[E-4 計画](2026-10-21-delivery-status.md)と `.superpowers/sdd/2026-10-21-delivery-status/report-to-user.md`、部分発送は [E-1 設計](../specs/2026-10-10-partial-fulfillment-design.md)。形式は G-1・G-2 計画に合わせる。G-4 の範囲（注文一覧12列・注文の詳細頁・返金/取消/返品/入替の入口の移設・全件CSV）は作らない。

**決めたこと（ruling）**

- 範囲は設計14章の G-3 行だけ（荷作り表・発送票・同梱・注文別メール・追跡の親・出荷日と訂正履歴・発送/取消/伝票訂正/手動配達済みの票単位での再開）。旧4RPC（`admin_create_fulfillment` / `admin_cancel_fulfillment` / `admin_update_fulfillment_tracking` / `admin_mark_fulfillment_delivered`）は `LEGACY_FULFILLMENT_DISABLED` のまま**再開しない**。旧HTTP入口4つ（`/api/admin/orders/[id]/fulfillments` の GET/POST と `…/[fulfillmentId]/cancel|tracking|delivered`）も 410 のまま残し、迂回口を作らない。新しい書込みは票単位の関数だけ。
- 移行は **4本**（`supabase/migrations/<ts1>_group_g3_shipping_foundation.sql`＝表・列・守り・割当イベントの理由・`item_delete_blockers`、見込み 55〜75 KB。`<ts2>_group_g3_shipping_reads.sql`＝読取と同梱/準備数の定義・追跡の読取側の置換、見込み 60〜85 KB。`<ts3>_group_g3_shipping_slips.sql`＝ロック helper・下書き・発送確定・取消、見込み 70〜95 KB。`<ts4>_group_g3_shipping_actions.sql`＝伝票訂正・手動配達済み・出荷日訂正・配送反映の置換・許可一覧・assert、見込み 70〜95 KB）。理由は(1)foundation は書込み口を持たず／reads は書込みを持たず／slips・actions が書込みを持つ、というレビュー境界、(2)長い置換関数（`record_delivery_read_result`、`get_order_delivery_detail`、`get_order_status_public_material`）を1本に積まず、レビューを読める大きさに保つため。**ファイルの大きさに上限は設けない**（本番は `npx.cmd supabase db push --linked` でファイルごとに1取引で当てるので、100 KB を超えても分ける必要はない。G-2 の2本目も100 KB を超えたまま同じ方法で適用済み）。バイト数と MD5 は記録し、150 KB を超えたらレビューの報告に書く（止めない）。各ファイルは自身の末尾 assert（`-- G3A/G3B/G3C/G3D_FINAL_ASSERT_BEGIN/END`）を持つ。
- **データを変える文は書かない**（清掃・補完・権限行の再投入なし）。本番の変更はスキーマだけ。例外の前提が1つある: `order_fulfillments.shipment_date` の CHECK（`legacy OR shipment_date IS NOT NULL`）は既存行を検証するので、**本番の `order_fulfillments` に `legacy` でない行が0件であること**が適用の前提（`legacy` の行はCHECKに当たらない）。G-1 の清掃後は旧4RPCが止まっていて新しい発送は作れないので0件のはず。Task 13 の読取（`select count(*) from public.order_fulfillments where not legacy`）で0件でなければ**適用せず止めて**件数だけ報告する（補完の文を足すと「データを変える」になり、件数提示とownerの明示確認が要る）。0件なら本番のデータは変わらず、owner確認は不要。
- **下書きはDBに保存する**（設計5-2の「下書きを用意」、2章の荷作り表の「発送票の下書き」の入口）。`shipment_slips.stage` は `draft | confirmed | cancelled | discarded` の4値。下書きは在庫を取り置かず、選択は票の行 `draft_lines jsonb`（`[{"orderItemId":uuid,"quantity":int}]`、orderItemId 昇順）に持ち、**確定の時に初めて `shipment_slip_lines` へ一度だけ書く**（確定後の数量変更は取消して新票）。有効期限は最後に保存してから**7日**（`expires_at`）。期限切れの下書きは確定できず（`GROUP_G_SLIP_DRAFT_EXPIRED`）、保存し直すと延びる。自動削除・cron は作らない。
- 同梱の判定とその理由コードは**DBに1か所**（`private.group_g_bundle_verdict(uuid[])`）。会員同士＝両方の `orders.user_id` が非NULLで同じ（メールが違ってもよい。別IDは同じメールでも不可）、ゲスト同士＝両方 `user_id IS NULL` で `lower(btrim(shipping_email))` が同じ、会員とゲストの混在は不可。配送先は `shipping_full_name・postal_code・prefecture・city・address・building・phone` の `btrim` 後の完全一致。必須7項目（メール・氏名・郵便番号・都道府県・市区町村・住所・電話。建物は任意。`private.order_has_required_shipping_fields` と同じ判定を、準備数の定義と同梱判定の両方で使う）のどれかが空の注文は `address_incomplete`（欠損を一致扱いにしない）。建物は空同士なら一致、片方だけ空なら不一致。会員の現在の住所は使わず、注文の配送スナップショットで比べる。別IDをメールで連鎖してまとめない。TS の純粋関数（`bundling.ts`）は画面の候補の絞り込み用の写しで、DB試験が同じ組合せでDBと突き合わせる。
- 「発送準備中の数」の定義も**1か所**（`private.group_g_shipment_ready(uuid[])`）: 注文が `paid`、`paid_at` あり、G-1 の品物状態の投影で `ready` の範囲、阻害理由 `payment_review`・`exchange_fee_waiting`・`variant_missing` が付かず、配送先が必須7項目（上と同じ `order_has_required_shipping_fields`）そろっていること（足りなければ行ごとに `address_incomplete`）。荷作り表・下書きの保存・発送確定が同じ関数を使う。取消申請中・返金処理中の数は投影が別状態に分けるので入らない。
- 割当の消費（Task 5 の `consume_group_g_allocations`）は `consume` イベントを足すだけで、台帳 `stock_movements` は足さない（空き在庫Fは動かない。手元の在庫＝F+A+H のAが発送数だけ減る）。**設計8-1の `shipment_slip_lines.参照割当` は列にしない**（1行が複数の割当にまたがりうる。参照は確定の操作の `consume` イベントそのもの）。**DBの守り**（G-1 持ち越し）: 遅延 constraint trigger `group_g_shipment_consumption` を `order_fulfillment_lines`（INSERT）・`order_fulfillments`（`cancelled_at` のUPDATE）・`order_item_allocation_events`（INSERT）に付け、commit 時に明細ごとに**等式** `取り消していない非legacyの発送行の数量の合計 = consume の合計 − restore の合計` を確かめる（違反は `GROUP_G_SHIPMENT_CONSUMPTION / 23514`、DETAIL の決め方は Task 1）。同じ票の発送は全部同時に取り消された状態だけを許す（`slip_partial_cancel`）。この守りは既存の材料・試験にも及ぶので Task 1 で付け替える。
- 発送の取消の戻し（Task 6 の `restore_group_g_shipment`）は、確定の操作の `consume` イベントごとに「台帳 `restock`（無タグ）→ 新しい割当 → 台帳 `purchase`/`exchange`（タグ付き）＋ `restore` イベント」の1組で、`reverses_event_id` の UNIQUE が「戻しは1回」を保証する。空き在庫Fは変わらず、手元の在庫だけ n 戻る。
- 注文の状態は既存の契約どおり: 全部送った発送（`completes_order`）で `orders.status='shipped'`・`shipped_at`・carrier/番号の写し、取消で未発送が戻れば `paid` に戻して3列をNULLにする。`app.order_change_reason` は既存の履歴表示と合わせて `admin_create_fulfillment`（確定）・`admin_cancel_fulfillment`（取消）・`admin_update_fulfillment_tracking`（伝票訂正）をそのまま使う。G の12状態を注文の enum へ書かない。
- 伝票番号の C-4 の書式は `^[0-9A-Za-z-]{1,64}$`（前後の空白を落とした後）。運送会社と番号は**両方入れるか両方空**（片方だけは `GROUP_G_SLIP_TRACKING_INCOMPLETE`）。そのため `order_fulfillments_tracking_check` を「`legacy OR (shipping_carrier IS NULL) = (tracking_number IS NULL)`」へ置き換える。番号なしの発送メールは追跡の3行を出さず、決まった後の入力で `shipping_update`（前の番号が無い時は「先にお知らせした伝票番号は使えません」を出さない）。
- 注文ごとの派生キー（再送で増えない）: 発送の `request_key` ＝ `md5('slip_fulfillment:' || 確定のrequest_key || ':' || order_id)::uuid`、伝票訂正の変更行の `request_key` ＝ `md5('slip_tracking:' || request_key || ':' || fulfillment_id)::uuid`、手動配達済みの出来事の `request_key` ＝ `md5('slip_delivered:' || request_key || ':' || fulfillment_id)::uuid`。発送メールは既存の「発送ごとに1通」の一意索引（`order_email_outbox` の `(fulfillment_id) WHERE origin='auto' AND kind='shipped'`）をそのまま使い、注文ごと1通になる。
- **追跡の親**（設計8-1の `private.shipment_tracking_registrations`）: 票×版に1行（UNIQUE）の**同一性と所属**の行（`slip_id, tracking_version, leader_fulfillment_id, carrier, tracking_number`）。外部登録・読取・停止の状態機械（`state`/`lease`/再試行）は**代表の発送（その票で `order_id` が最小の有効な発送）の既存E-4の行**（`private.fulfillment_tracking_registrations`）が持ち、E-4 の worker と7つのRPCを変えない。その票の他の発送（参加）には登録行を作らない。参加の発送へ状況・出来事・メール・配達済みの操作を広げるのは、`record_delivery_read_result` の置換（Task 8）と、読取側（`get_order_delivery_detail`・`get_order_status_public_material`）が `private.tracking_registration_owner` で代表の行を引く置換。**設計の「登録状態・lease・再送情報を親が持つ」との差**で、理由は E-4 の worker と7関数の全面書換えを避けるため、誤りなら親の列を足して代表の行を移す。要対応（`order_fulfillment_attention`）は代表の発送にだけ付け、票の画面に出す（他の注文の発送には広げない。広げる関数は advisory を持たない非書込み経路で行を取り合うため）。追跡がオフでも親の行は作る（番号がある版のみ）。
- 出荷日: `shipment_date`（JST の暦日）は発送ごと・票ごとに持つ。確定時の初期値は JST の今日、範囲は全対象注文で `(paid_at AT TIME ZONE 'Asia/Tokyo')::date <= 出荷日 <= (now() AT TIME ZONE 'Asia/Tokyo')::date`（`paid_at` 欠落・未払いは発送不可）。`confirmed_at`＝`shipped_at`＝確定の操作時刻で、出荷日を過去にしても、訂正しても**変えない**（返品期限の起点は `shipped_at`／届いた日のまま。KPI・会計の注文日基準は変えない）。初回は `shipment_date_history` に kind `initial`（前の日付＝初期値の今日、新しい日付＝入力値、理由なし）を必ず書く（初期値から変えた場合も経緯が残る）。訂正は `admin.shipping.correct_date`（店長のみ）・理由必須・kind `correction`。配達済みの日（JST）より後への訂正は理由だけで通さず `GROUP_G_SHIPMENT_DATE_AFTER_DELIVERY`。会計入力は `list_shipment_accounting_inputs`（DB関数のみ。HTTP窓口は作らない）。
- 旧クライアントの整理: `useDeliverySubmission` は新しい票の画面（伝票訂正・配達済み）が**再利用**するので残す（G-1 持ち越しの「未使用 export」から外れる）。`COMPLETION_RECORDED_MESSAGE`・`NO_COMPLETION_QUANTITY_MESSAGE`・停止stubの `callFulfillmentApi`・`fetchFulfillmentMaterials`・`submitTrackingEdit`・`submitManualDelivered` と、他から使われなくなった旧型は、`grep` で使用箇所が0件になったものだけ削除する。`LEGACY_FULFILLMENT_DISABLED_TEXT`（410の本文・旧入口の案内）は「公開まで」を「終わりました。荷作り表の発送票から行ってください」へ置換し、旧HTTP入口は 410 のまま。
- 申し送り（G-1）の「再構築する守り」と本計画の対応: 取消で登録を cancelled・要対応を auto で閉じる・未送信の発送メールを skipped（Task 6）／取消の断り（旧 `FULFILLMENT_HAS_RETURN`・`FULFILLMENT_REFUNDED` は票単位の `GROUP_G_SLIP_HAS_RETURN`・`GROUP_G_SLIP_REFUNDED`）（Task 6）／作成で交換の手数料待ちを止める（`GROUP_G_SLIP_EXCHANGE_ON_HOLD`、Task 4・5）／要求の指紋の再送判定（`group_g_operations` の `request_key + fingerprint`、全writer）／C-4 書式（Task 5・7）／発送行は consume で裏付ける DB の守り（Task 1）。G-2 持ち越し M1（`item_delete_blockers` が発注書を見ない）は Task 1。
- 資料の食い違い（実装者は計画の値に従う）: (a) ブランド資料は `docs/01_Planning/brand.md`（CLAUDE.mdの `docs\1_RequirementsDifinition\brand.md` は無い）、(b) `scripts/trace/scope.json` の領域（NEWS・HOME・LOOK・ABOUT・STOCKIST・SEARCH・PRIVACY・AUTH・ADMIN の列挙パス）に G-3 の新規・変更ファイルは入らない（ADMIN は create-user・revoke-user-sessions・audit-logs・users/mfa・contact・item-color-presets だけ）ので、要求は `docs/02_Requirements/requirements.md` の6列の表に足す方式、(c) 設計 8-1 の `shipment_slips` の「段階」は上の4値、(d) 現在の route は 145 ファイル・186 メソッド（G-3 で 155 ファイル・197 メソッド）。

## Review Focus

- **ロック順とG-1・G-2の書き手との競合:** 票の書込み10本と置換する `record_delivery_read_result` が共通advisoryより前に行lockを持たないこと。確定・取消・訂正が在庫の閉包を取ってから票の行→代表の登録の行の順で取り、受取/受取の取消/棚卸減/入金/返金/返品の書き手と逆順の待ちが無いこと。注文順が逆の2つの票でdeadlockが0 → Task 4〜10（別接続でadvisory待ちを確認→票/注文/variant/割当をNOWAITで取れる）。
- **二重発送と再送:** 同じ明細を2つの下書きが選んでも先に確定した分を超えて発送できないこと。同じ `request_key` の再送・通信切断後の再送・二重クリックで割当の消費・発送行・outboxが増えないこと。通知オンの票は注文ごとに発送メールがちょうど1通 → Task 5・10・11・12。
- **同梱の拒否（サーバー）:** 会員と別会員、会員とゲスト、ゲストのメール違い、別住所（7項目それぞれ）、欠損（空）、建物の片方空を、画面を通さない呼出しでも拒否すること。別IDをメールで連鎖しないこと → Task 2・4・5。
- **出荷日のJST境界:** 入金が日本時間の 23:59:59／00:00:00 をまたぐ時、複数注文の最も遅い入金日が下限になること、今日（JST）の上限、交換手数料の入金後も下限が元の `paid_at` のままなこと、訂正の再検証、配達日より後の拒否 → Task 5・9・12。
- **取消の拒否と戻しの1回:** 返品・発送後返金のある注文が1つでもあれば票全体を拒否し何も変えないこと。戻しは1回だけで手元の在庫が n 戻り空き在庫は変わらないこと。取消後に同じ品物を新票で再発送でき、番号が `n+1` になること → Task 6。
- **他の注文の情報の漏洩:** 同梱票のお客様向け画面（注文詳細・状況ページ）と発送/更新/配達のメールに、同じ票の別注文の注文番号・品物・氏名・住所・伝票以外の情報が出ないこと。管理の票の画面だけが全注文を見せること → Task 3・5・8・11・12。
- **追跡の親:** 追跡オンの票で外部登録が票×版に1回（代表の行だけ）であること、結果は票の全注文へ反映され参加の注文のお客様にも状況が出ること、訂正で旧版の通知を現行へ適用しないこと、取消で代表の登録だけが cancelled になり外への停止の印が付くこと、追跡オフでも全操作が動くこと → Task 7・8。
