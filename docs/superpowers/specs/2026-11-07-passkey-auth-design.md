## 概要

お客さん・サポーター・店長の全員を、パスワードからパスキーに置き換える。パスワードはなくす。

| 項目 | 内容 |
| --- | --- |
| なぜ | パスワードは、盗まれる・使い回される・だましのページで抜かれるのが一番多い入口。パスキーは端末の鍵で入るので、だましのページでは使えない。NIST・OWASP ともに一番強い方法として挙げている |
| お客さん | パスキーで入る。予備はメールに届く8桁のコード。Google でも入れる。コードで入ったらパスキーを作るように勧める |
| 店員（店長・サポーター。同じ扱い） | パスキーだけで入る。2本以上を持つ。メールのコード・Google・パスワード・認証アプリでは入れない |
| 店員のやり直し | パスキーを全部なくした店員は、店長がやり直しの手続きを出す。店長本人の最後の手段は Supabase のダッシュボード |
| 店員のログインの長さ | 入ってから最長24時間。何もしないで1時間たったら入り直し |
| 知らせ | パスキーを足した・消したら、本人にメールで知らせる。店員の場合は店長にも知らせる |
| 使う物 | Supabase のパスキー（ベータ版）。`@supabase/supabase-js` を上げる（パスキーの方法の形を試しで確かめた 2.119.0 に固定する。ベータ版なので上げる時は E2E を全部流す） |
| 一番大事な仕組み | 店員のログインの状態は、パスキーで入った時だけ作られる。これを Supabase の「トークンを出す前の確かめ」（Custom Access Token フック）1か所で締める。店員のパスキーは、アプリの窓口で登録した物だけを有効にする（5-5） |
| 順番 | 最初に手元で試し（4-1。2026-11-16 に済み。段1に進めない崩れは無い。6-2 手順3 と 5-1 を直した）。次は段1の計画 |

## 1. 目的と、しないこと

### 1-1 目的

- だましのページ・パスワードの使い回し・パスワードの総当たりで、アカウントを取られないようにする
- 店員のアカウントは、パスキー以外のどの道からも入れないようにする（管理画面は注文・返金・お客さんの住所を扱うため）
- お客さんは、パスキーが無くてもメールのコードか Google で入れるようにする（手軽さを落とさない）

### 1-2 しないこと

- お客さんのログインの長さは変えない（今と同じ。7日間、使うたびに延びる）
- 決済・カート・お気に入り・ゲストの注文の仕組みは変えない
- 権限（だれが何をできるか）の表と割り当ては変えない
- 店員の Google Workspace によるログイン（会社が配る Google アカウント）は入れない。今は店員が数人なので、パスキーだけのほうが簡単で強い
- お客さんの Shop Pay のような外のサービスのパスキーは使わない

### 1-3 失敗とみなすこと

- 店員が、メールのコード・Google・パスワード・やり直しのメールのどれかだけで管理画面に入れる
- 店員のアカウントに、本人も店長も知らないうちにパスキーが足される
- 店員が全員パスキーをなくして、ダッシュボードの手順でも戻れない
- お客さんが、パスキーを作らないと買い物できない
- 試験（E2E）が手元の Supabase で流せなくなる

## 2. 基準と、ほかの所との比べ

調べた日は 2026-11-06〜07。

### 2-1 NIST・OWASP

| 項目 | NIST SP 800-63B-4 | OWASP | この設計 |
| --- | --- | --- | --- |
| だましに強い方法 | AAL2 では、だましに強い方法を選べるようにする（SHALL） | FIDO2/WebAuthn を一番に勧める | 全員がパスキーを使える。店員はパスキーだけ |
| パスキーを「2要素」と数える条件 | 端末で本人確認（顔・指紋・PIN）をした印（UV）がある時だけ。無ければ1要素 | 同じ考え | 全員、UV の印を必須にする（5-3） |
| メールのコード | 本人確認の手段に使ってはならない（SHALL NOT） | 弱い。ASVS L3 は認証に使わない | 店員には使わない。お客さんの予備としてだけ使う（Shopify と同じ） |
| コードの長さ・期限 | 6桁以上・10分以内 | 20ビット以上・10分以内 | 8桁・5分（今のまま） |
| ログインの長さ（AAL2） | 全体24時間以内・無操作1時間以内（SHOULD） | 事務用は全体4〜8時間・無操作15〜30分が目安 | 店員は24時間・1時間（NIST の上限）。オーナーの決定 |
| 管理者の多要素 | — | 管理者には必ず求める | 店員はパスキーだけで入る。UV の印で2要素にする |
| やり直し | — | やり直しで多要素を飛ばせてはならない。要素の変更は危険度が高い操作 | 店員のやり直しは店長だけが出せる。足す・消すは知らせる |

出典: [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b/)、[NIST の同期型パスキー](https://pages.nist.gov/800-63-4/sp800-63b/syncable/)、[NIST のセッション](https://pages.nist.gov/800-63-4/sp800-63b/session/)、[OWASP ASVS 5.0](https://owasp.org/www-project-application-security-verification-standard/)、[OWASP MFA Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)、[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## 3. オーナーが決めたこと（2026-11-06〜07）

1. 全員パスキーにする。パスワードはなくす
2. お客さん: パスキーで入る。予備はメールの8桁のコード。コードで入ったらパスキーを作るように勧める。Google は残す。パスキーを足した・消したらメールで知らせる。ログインの長さは今のまま
3. 店員（店長・サポーターは同じ扱い）: パスキーだけ。2本以上。メールの予備は無し
4. 店員のやり直しは店長が出す。店長本人の最後の手段は Supabase のダッシュボード
5. 店員のログインは最長24時間・無操作1時間
6. 店員のパスキーを足した・消したら、本人と店長に知らせる
7. 店員の認証アプリ（TOTP）と Google はなくす
8. Supabase のパスキー（ベータ版）を使う。supabase-js を上げる

### 4-3 本番の DB に当てる時

段1の移行（フックと、管理の入口の判定の変更）を本番に当てると、本番ではパスキーを有効にするまで、だれも管理の権限を持てない。お客さんのパスワードも使えなくなる。

- 2026-11-07 時点で、普段の開発（`npm run dev`）は本番の DB を向いている。このまま当てると、店長が開発の画面で管理画面に入れなくなる。
- だから本番に当てるのは、開発を手元の Supabase に切り替えた後にする（会計の前提として 2026-11-05 にオーナーが決めた切り替えと同じ物）。切り替えの前は、移行を本番に当てず、push もしない。
- 本番のアプリはまだ公開していないので、切り替えた後なら本番に当てても困る人はいない。

## 5. 全体の仕組み

### 5-1 ログインの状態は必ずアプリを通して作る

今の決まり（ADR-0417・0419: アプリが GoTrue のセッションを自分の Cookie と `public.sessions` の行に結び付け、結び付いていないセッションは API でも DB でも拒否）をそのまま守る。

- パスキーのログインは、低い層の API（`passkey.startAuthentication` → ブラウザの WebAuthn → `passkey.verifyAuthentication`）を使う。
  - 終わり（検証）は、必ずアプリのサーバーの窓口を通す。
  - 始め（選択肢を取る）は、**オーナーが2026-11-16 に決めた**次の道にする（[試しの結果](2026-11-16-passkey-local-trial-results.md)の T7 と、[回数の制限の調べ](2026-11-16-passkey-rate-limit-research.md)に基づく）。
    - 背景: GoTrue の始めの回数の制限は IP ごとに5分30回（`GOTRUE_RATE_LIMIT_PASSKEY`）。上げる設定は、API・ダッシュボード・CLI の設定のどれにも項目が無い（確定）。ホスト版でオーナーが値を変えられないことは有力（API を呼んで確かめてはいない）。サーバーの呼び出しは管理者の鍵でも免除されない（ソースで確認。有力）ので、添え書き無しのサーバー呼びは、全員が1つの IP から出て、店全体で5分30回になる見込み。
    - **3つの道のうち、(a) に決定**: (a) 店のサーバーが新しい秘密の鍵（`sb_secret_`）で始めを呼び、お客さんの IP を `Sb-Forwarded-For` に添える。お客さんごとに数えられ、店全体の制限にならない。`sb_secret_` は captcha が免除されるので Turnstile は付けない（手元で実測）。この添え書きは `sb_secret_` でだけ受け付けられ、プロジェクトの設定で有効にする必要がある。(b) ブラウザから GoTrue を直に呼び、見えない形の Turnstile のトークンを本文（`gotrue_meta_security.captcha_token`）で渡す。(c) 添え書き無しでサーバーから呼ぶ（店全体で5分30回になるので採らない）。
    - **(a) の窓口の決まり**（段1で作る）:
      - お客さんの IP は、今の決まりの ADR-0416 の `getClientIp`（Vercel の見出しだけから取る）で取る。利用者が付けた見出しは信用しない。
      - IP が取れない（`null`）時は、添え書き無しで呼ばず、断る（添え書き無しだと店全体の1つの枠に落ちるため）。
      - 始めに使う鍵は `sb_secret_` で始まる物だけにする。古い `service_role` の JWT では添え書きが効かない。アプリは起動時に鍵の形を確かめ、違えば (a) の始めの窓口だけを断る（アプリ全体は止めない。ほかの窓口は今の鍵のまま動く）。手元は添え書きの設定が入れられず測れないので、鍵の形の誤りは手元の試験では見つからない。
      - アプリの側でも、始めの窓口に IP ごとの回数の制限を付ける（今の `rateLimit.ts`。値は作り手が決める。IP が取れない時は断る。オーナーが2026-11-16 に確認済み）。GoTrue の制限より前に、荒い要求を止めるため。これは (a) の窓口の制限で、(b)（ブラウザから直に呼ぶ）には効かない。GoTrue が始めで 429 を返した時は、今のログインの回数の制限と同じ文言に直して出す。
    - **(b) は段1で先に作っておき、設定で切り替えられるようにする**（オーナーが2026-11-16 に決定）。本番の確認（8-2）で添え書きが効かなかった時は、設定を変えるだけで (b) に切り替わる。(b) のために段1で作り、確かめること:
      - ブラウザから始め、サーバーで終わる組み合わせ（始めと終わりの呼び手が違う）は、試しでは測っていない（試しは同じ呼び手で流した）。段1の試験で、`challenge_id` が呼び手に結ばれず終わりが通ることを確かめる。
      - ブラウザから Supabase に直につなぐための CSP の `connect-src`。本番の GoTrue で captcha を有効にすること（今は captcha の段階 B の待ち）。
      - 本番で `sb_secret_` が captcha を免除されなかった時（8-2 の2）は、(a) の始めにも Turnstile のトークンが要る。その時は、サーバーが受けたトークンを本文で GoTrue に渡す形に直す（ブラウザの見えない形の Turnstile は (b) と同じ。これは推論で、試していない。道そのものはオーナーが2026-11-16 に確認済み）。
    - **本番で添え書きが効かなかった時**（8-2 の確認）は、(b) に切り替える（設定の変更だけ）。
    - どちらでも、ログインの終わり（検証）は必ずアプリのサーバーの窓口を通す。
  - ブラウザは鍵の操作だけをする。
- 検証に通ったら、今の `persistSessionAndCookies()` で結び付けを書く。
- 登録も、アプリのサーバーの窓口を通す（ログイン中の本人のトークンで GoTrue を呼ぶ）。

### 5-2 店員の締め付け（フック）

Custom Access Token フック（Postgres の関数。無料のプランで使える）を1つ置く。トークンを出す時（ログイン時と更新時）に毎回走る。

| 相手 | `amr` の中身 | 結果 |
| --- | --- | --- |
| 店員（`user_roles` で有効な admin・supporter） | `passkey` があり、そのログインから24時間以内 | 出す。アプリが認めたパスキー（5-5）が2本以上あるかを独自の印として JWT に入れる |
| 店員 | アプリが開けた「登録の窓」（6-2。リンクを押した時に開く）が開いていて、そのセッションの `session_id` が窓の行に控えた物と同じ | 出す（パスキーの登録しかできない。管理の権限は無い） |
| 店員 | それ以外（`otp`・`oauth`・`password`、24時間を超えた `passkey`、窓が閉じた招待） | 拒否 |
| お客さん | `password` | 拒否（パスワードは廃止。アプリには入口が無いが、GoTrue を直に叩く道を閉じる）。**有効にするのは段4**（4-2。段1〜3 では今のログインを壊さないため通す） |
| お客さん | それ以外 | 出す（今のまま） |

これで、メールのコード・Google・パスワード・GoTrue の直叩きのどれでも、店員のログインの状態は作れない。Google の自動のつなぎ（同じ確認済みメールの Google を同じアカウントにつなぐ。Supabase の仕様で止められない）が起きても、店員としてのトークンは出ない。

- 予備（T2 で崩れた時。T2 は PASS したので使わない）: アプリの結び付け（5-1）で店員のパスキー以外の結び付けを書かず、`private.app_session_is_live` で店員のパスキー以外を拒否する。この場合 GoTrue を直に叩けばトークンは出るが、API と RLS は通らない。
- 窓はセッションの `session_id` に結ぶ。ユーザーだけに結ぶと、窓が開いている間は、店員のふだんのメールのコードでもトークンが出てしまうため。窓の長さは30分（6-2 手順3。オーナーが2026-11-16 に確認済み）。窓の行の `session_id` は、**アプリがセッションを作った後に、分かったその番号で書く**（6-2 手順 3。案 B に決定）。フックが「最初に来たセッション」に結ぶ形（案 A）は採らない。
- 管理の入口の判定を変える。今は「`aal` が `aal2` か」を見ている（アプリは `admin-rbac.ts`、DB は `has_permission`）。これを次の3つ全部に変える。結び付き（ADR-0418 の後半）はそのまま。
  1. `amr` に `passkey` がある
  2. そのパスキーのログインの時刻から24時間以内（6-2）
  3. フックが入れた「認めたパスキーが2本以上」の印がある（6-2 の「1本しか無い店員」を API と RLS でも止めるため）
- **試しで分かったこと（2026-11-16。[結果](2026-11-16-passkey-local-trial-results.md)の T1〜T3）**
  - JWT の `aal` は `aal1`（パスキーは1段）。`amr` は `[{"method":"passkey","timestamp":<秒>}]` の配列で、`auth.jwt()->'amr'` で RLS から読める（確定）。上の2つ目の条件の「24時間以内」は、この `timestamp`（ログインの時刻。更新しても変わらない）で比べる。
  - フックの入力に、`claims` の中の `session_id` が入る。フックの入力の最上位は `claims`・`user_id`・`metadata`・`authentication_method`。`authentication_method` は、パスキーのログインで `passkey`、更新で `token_refresh`、メールのリンクとメールのコードの両方で `otp`、パスワードで `password`（メールのリンクとコードはフックでは区別できない）。
  - 拒否の応答は HTTP 403・`AuthApiError`・`code` は `unknown`・`message` にフックの文がそのまま入る。アプリが「店員はパスキーで」と見分けるには、文の中身で見分ける（6-2 の「ふだんのログイン」）。見分けが言い回しに頼らないよう、フックの拒否の文の頭に決まった印の文字列を付ける（段1で決める）。
  - **拒否された更新は、GoTrue のセッションを終わらせない**（確定）。セッションの行は残り、同じ更新トークンを再度送っても同じ拒否が返る。だから `private.app_session_is_live`（セッションが生きているかを調べる関数）だけでは、24時間を超えた店員を切れない。**拒否の後も、前に出したアクセストークンが残る間（最長1時間）に店員を止めるのは、上の2つ目の条件（`amr` の `passkey` の時刻から24時間）を、API と RLS の両方で必ず作ること**。期限内の JWT のままでも、RLS の側で時刻の比べで止められることは T3 で確かめた。
  - フックが更新を拒否した時に、アプリがそのセッションを終わらせるかは、段1で決める（今のままだと拒否されたセッションの行は残り続ける）。
  - フックに要った権限: `supabase_auth_admin` に、関数の `execute`、フックが読む表の `select`、記録の表の `insert`（窓の表の `select` は、外して試していない推論）。案 B ではフックは窓の表を書かないので、窓の表の `update` は要らない。フックの関数の `execute` は `public`・`authenticated`・`anon` から外す。
  - GoTrue は、パスキーの回数（sign count）の逆戻りによる複製の検知をしない（有力。ソースで確かめた。動かして確かめていない）。
  - 設定の表（上限の時間など）は、ログインした人に直に読ませず、`security definer` の関数で読ませる（段1の作り方）。
  - 段1の試験に入れること（試しで測っていない物）: 独自の印が `false` になる側、お客さんの本物の更新（`token_refresh`）、拒否された更新の後のセッションの扱い、拒否の後の前のアクセストークンで `/auth/v1/user` と `/rest/v1` を呼ぶこと、`auth.sessions.not_after`、本物の Google ログイン（`oauth`。8-2）。

### 5-3 顔・指紋・PIN の確かめ（UV）を必須にする

Supabase はパスキーの UV を「あれば使う」（preferred）にしていて、PIN の無い物理キーでも通る（確定。ソースで確認）。NIST の考えでは、UV が無いパスキーは1要素にすぎない。

- アプリの始めの窓口（5-1 で決めた (a) の道。サーバーが始めを呼ぶ）で、ブラウザに渡す選択肢の `userVerification` を `required` に書き換える。本番で (b) に切り替えた場合は、始めがブラウザから GoTrue への直の呼び出しになるので、この書き換えはブラウザ側の処理になる（守りの本体はサーバーの終わりの門なので崩れない）。
- 終わりの窓口で、届いた `authenticatorData` の UV の印を読み、無ければ GoTrue に渡す前に拒否する。印は `authenticatorData` の先頭から数えて**位置 32（33バイト目）の flags の `0x04`**（前の32バイトは相手の名前の指紋、flags の後ろ4バイトが回数）。
- 印は GoTrue が署名を確かめる同じバイト列なので、書き換えれば GoTrue の検証で落ちる。だからアプリの読み取りは信用できる。**T4 で確かめた**（ソフトの認証器。2026-11-16）: GoTrue は `preferred` のままだと UV 無しのログインも通す（UV の印は `false`）。印が `false` なら終わりの窓口を呼ばずに拒否する門では、GoTrue への呼び出しは0回。UV の印を無理に立ててログインを送ると、署名の検証で 400 `webauthn_verification_failed`。UV の無い認証器に `required` の選択肢を渡すと、ブラウザが `NotAllowedError` で止まる。
- 登録の応答は、UV の印を書き換えても通る（attestation が `none` で署名が無いため。確定）。本当の守りはログインの確かめで、登録の確かめは参考。
- 登録の時も同じく UV を必須にする。
- 全員に適用する（スマホ・PC のパスキーは、いつも顔・指紋・PIN を求めるので、お客さんの手間は増えない）。
- **物理キー**: 確かめたのはソフトの認証器だけ。PIN の無い物理キーの挙動（UV の印、一覧を渡さないログイン）は、開店前に足す確認にする（8-2）。物理キーで違いがあっても、サーバーの門が UV の印で断るので守りは崩れない。困るのは「PIN の無いキーの人が入れない」ことと「一覧を渡さないログインが動くか」。
- この確かめは、ログインの状態を必ずアプリを通して作る決まり（5-1、ADR-0417・0419）に頼っている。GoTrue を直に呼べば UV の無いパスキーのセッションは作れるが、アプリに結び付かないので API でも RLS でも使えない。結び付けの旗（`AUTH_REQUIRE_APP_SESSION`）を切ると、UV の必須も効かなくなる。このことを新しい ADR に書く。

### 5-4 パスキーの足し・消しの知らせ

GoTrue には、パスキーの通知もフックも無い（確定）。アプリの窓口だけで知らせると、GoTrue を直に叩いた足し・消しを見落とす。

- DB の側で拾う。**`auth.webauthn_credentials` への引き金（表が変わった時に自動で動く仕掛け）を採る**（T5 で、`postgres` で作れて、本人・管理 API・SQL の直・ユーザー削除の連鎖の全部を拾えた。オーナーが2026-11-16 に承認）。監査の記録（`auth.audit_log_entries`）は、SQL の直の削除を残さず、ユーザー削除の連鎖ではパスキーの行が残らないので採らない。
  - 知らせるのは、行の追加と削除。回数（sign count）と最後に使った時刻だけの更新は、ログインのたびに起きる雑音なので知らせから外す。
  - `public_key`・`credential_id` が変わった更新は、鍵そのものの差し替えなので、別に拾って知らせる（名前の変更とは別扱い）。
  - 拾えない道（盲点）: `TRUNCATE`（行ごとの引き金が動かない）、`ALTER TABLE ... DISABLE TRIGGER`、`session_replication_role = replica`（いずれも強い権限の人だけ）。残る危険として 10 に書く。
  - 本番でできるか、GoTrue の更新で引き金が消えないかは、8-2 で確かめる。
- 拾った足し・消しを、今の注文メールと同じ「送る予定の表」（outbox）に積み、アプリが送る。
- 宛先: お客さんは本人。店員は本人と、有効な店長（admin）全員。
- 文面: 「パスキーが追加されました（名前・日時）。心当たりが無ければ、すぐに店長へ」など。お客さん向けと店員向けで分ける。
- 遅れは数分まで許す（私の判断）。

### 5-5 店員のパスキーは、アプリで登録した物だけ有効にする

盗まれたセッションのままパスキーを足されると、24時間の上限を越えて入り続けられてしまう。GoTrue の登録の窓口は、ログイン中なら直に叩けるので、アプリの画面で止めるだけでは足りない。

- 店員がアプリの窓口でパスキーを登録したら、その鍵の ID をアプリの表（`private` の下）に控える。これを「認めたパスキー」と呼ぶ。
- 店員がパスキーで入る時、アプリの終わりの窓口は、届いた鍵の ID が認めたパスキーの表にあるかを確かめる。無ければ拒否する。GoTrue を直に叩いて足したパスキーでは、店員としては入れない。
- 店員がアプリの窓口でパスキーを足す時は、直前（5分以内）にパスキーで入り直したことを求める（OWASP の「要素の変更は危険度が高い操作」）。登録の窓（6-2）の中の最初の2本は除く。
- 認めたパスキーの本数（2本以上か）は、この表で数える。フックはこの表を読んで印を JWT に入れる（5-2）。
- GoTrue を直に叩いて足された鍵は、知らせ（5-4）で店員と店長に届く。
- お客さんには、この表を使わない。お客さんがパスキーを足す時は、直前（10分以内）にパスキーかメールのコードで入ったことを、アプリの窓口で求める（私の判断）。

## 6. 流れ

### 6-1 お客さん

**ログイン（`/login`）**

- 「パスキーでログイン」のボタン、「Google でログイン」のボタン、「メールでコードを受け取る」の入口を並べる。
- パスキーはボタンを押してから始める。画面を開いた時の自動の候補（conditional UI）は使わない。選択肢の期限（5分）が切れやすく、captcha とも合わないため（私の判断）。
- パスキーのログインの Turnstile: **付けない**（オーナーが2026-11-16 に決めた 5-1 の (a)。始めはサーバーから `sb_secret_` で呼ぶ）。GoTrue の captcha は管理者の鍵（古い `service_role` の JWT も `sb_secret_` も、手元で実測）の呼び出しを免除する。鍵が無ければ通らないので、ボットの対策は窓口の回数の制限で足りる（ADR-0420 と同じ考え）。
- GoTrue の captcha が見るのは、パスキーのログインの**始めだけ**。終わり（ログイン・登録）と登録の始めには、Turnstile のトークンは要らない（確定。ソースでも確認）。
- 本番で添え書きが効かず 5-1 の (b)（ブラウザから直に呼ぶ）に切り替えた時は、見えない形の Turnstile を付ける。トークンは本文の `gotrue_meta_security.captcha_token`（supabase-js の `options.captchaToken`）で渡す。見出しでは渡せない（手元で実測）。

**メールのコード（予備と新規の両方）**

- メールアドレスを入れる → Turnstile → 8桁のコード（5分）→ 入れる → ログイン。
- 登録が無いアドレスなら、この流れでアカウントを作る（Shopify と同じ。登録の画面とパスワードを無くす。私の判断）。今の登録の画面にパスワード以外の欄（同意など）があれば、この流れに移す。
- 登録済みかどうかで、画面も応答も変えない（列挙対策。今の SEC-AUTH-016 を保つ）。
- 今の「保留の Cookie・再送・総当たりの制限」（ADR-0400〜0402）は、コードの段だけに作り直して使う。

**コードで入った後**

- パスキーが1本も無ければ、「パスキーを作る / あとで」の画面を出す。コードで入るたびに出す（私の判断）。
- 作る時は UV 必須（5-3）。名前は端末名を初期値にする。

**アカウントの画面**

- パスキーの一覧（名前・作った日）。名前の変更・削除・追加。
- 最後の1本も消せる（メールのコードが残るため）。
- 今の `/account/password` は消す。

**Google**

- 今のまま。コードを求めない（今の挙動。未決だった SEC-AUTH-008 は「お客さんの Google はコード無し」で閉じる）。

### 6-2 店員

**招待（新しい店員）**

1. 店長が管理画面の「ユーザー」で、メールと役割（店長・サポーター）を入れて招待する。今の `/admin/create-user`（パスワードを直に入れる）は消す。
   - アドレスにアカウントが無ければ、パスワードの無いアカウントを作る。こちらも役割は招待の行に控えるだけにする（手順3の③で有効にする）。
   - すでにお客さんのアカウントがあれば、同じアカウントを使う。役割は、この時点では有効にせず、招待の行に控えるだけにする（手順3の③で有効にする）。GoTrue の招待（`inviteUserByEmail`）は確認済みのアドレスを断るので使わない。
2. アプリが使い切りの招待の合言葉を作り、メールで送る。期限は24時間（私の判断）。GoTrue のメールのリンクはコードと同じ5分で切れるので、そのままは使えない。
3. 店員がリンクを開き、画面のボタンを押す。**30分の窓を数え始め、セッションを作るのは、ボタンの POST の時だけ。メールのリンクの GET では何もしない**（メールのリンクを先に読みに行く機械で、合言葉が使い切られないため。今の再設定の合言葉と同じ形）。アプリが合言葉を確かめ、その場で GoTrue のセッションを作る（`admin.generateLink` の magiclink を作って、サーバーですぐ検証する）。**窓の開け方は案 B（オーナーが2026-11-16 に決定）**: ①先にお客さんの扱いのまま（店員の役割が無い状態）でセッションを作る → ②検証で分かった `session_id` に結んで、「登録の窓」を開ける（`private` の表に、だれの・どのセッションの・いつまでの窓かを置く。**窓の長さは30分。ボタンの POST の時から数える**。オーナーが2026-11-16 に確認済み。アクセストークンは窓より長く（最長1時間）残るので、**登録の窓口は、呼ばれるたびに窓の行がまだ有効かを確かめ直す**。切れた時は、パスキーが0本のときだけ、店長が招待かやり直しを出し直す）→ ③最後に店員の役割を有効にする。
   - 先に窓を `session_id` 無しで開け、フックが最初に来たセッションに結ぶ形（案 A）は採らない。T6 の実測で、窓が空の間に同じ人のメールのコードのセッションが先に来ると、そのセッションが窓に結ばれ、パスキー無しで発行された。フックの入力では、メールのリンクとメールのコードは区別できない（どちらも `authentication_method` が `otp`）。招待の検証が失敗した後も窓が相手のセッションに結ばれたまま残ると、5-5 の「窓の中の最初の2本」と合わさり、相手が自分の鍵を足せる道になる。案 B は、既知の `session_id` に先に結ぶので、この競りが無い。
   - すでに店員の役割が有効な人（やり直しなど）は、①でフックに拒否されるので、**やり直しの手順で先に役割を止めておく**（下）。
   - 役割を切り替える時の監査・知らせの副作用は、試しで測っていない。招待は段3なので、段3で確かめる。
4. 店員は登録の画面で、パスキーを2本登録する。別の端末かセキュリティキーを勧める。2本とも認めたパスキー（5-5）に控える。招待のセッションで2本登録できることは T6 で確かめた（2本の間で認証器を替えても通った）。
5. 2本そろったら、窓を閉じ、そのセッションを終わらせ、パスキーでのログインに送る（そのセッションの `amr` は `passkey` が付かず、メールのリンクの `otp` のままのため。T6 で、2本登録した後に更新した JWT でも `otp` だけと確かめた）。窓が開いている間の更新は通り、窓の行を消した後の更新は拒否される（T6）。

**今いる人を店員に上げる時**

- 今の「ユーザー」の役割の変更（`PATCH /api/admin/users`）で、お客さん（`user`）を店長・サポーターに上げることは、今も残す。ただし、この窓口は役割を直に変えず、**招待の行を作る**（役割は手順3の③で有効にする）。
- ただし上げる時は、必ずやり直し（下）と同じことをする。その人のパスキーを全部消し、ログインを全部終わらせ、合言葉のメールを出す（役割は、手順3の③で有効にするまで付けない。窓はリンクを押した時に開く）。お客さんとして作ったパスキーや、自動でつながった Google を、店員の入口として持ち越さないため。
- 店員からお客さんに下げる時は、認めたパスキーの表からその人の行を消し、ログインを全部終わらせる。

**ふだんのログイン**

- お客さんと同じ `/login` の「パスキーでログイン」を使う。入った後、店員は管理画面へ。
- 店員がメールのコードや Google を試したら、「店員はパスキーでログインしてください」と出す（フックで拒否された応答を、アプリがこの文に直す）。

**パスキーの管理**

- 自分のパスキーの一覧・追加・名前の変更・削除。
- 削除で2本を切る時は、画面で止める。GoTrue を直に叩かれると止められないので、知らせ（5-4）で気づけるようにする。直に消された鍵は、認めたパスキーの表からも消す（5-4 で拾った時）。
- 認めたパスキーが1本しか無い店員がパスキーで入ったら、「もう1本登録してください」の画面に送る。管理の権限は、画面だけでなく API と RLS でも無い（5-2 の3つ目の条件。私の判断）。

**やり直し（パスキーを全部なくした店員）**

1. 店長が「ユーザー」で、その店員の「パスキーを全部消してやり直す」を押す。確認の語と理由（10〜500字）を入れる（今の MFA のやり直し ADR-0457・0461 と同じ守り。今は画面が無いので作る）。
2. アプリがその店員のパスキーを全部消し、ログインを全部終わらせ、**店員の役割を止め**、招待と同じ合言葉のメールを送る。窓はリンクを押した時に、招待の手順3のとおり開ける（役割は③で有効に戻す）。役割を止めるのは、店員のままだと手順3の①のセッションがフックに拒否されるため。
3. 後は招待の 3〜5 と同じ。
4. 自分自身のやり直しはできない（今と同じ）。

**店長本人の最後の手段**

- ほかに店長がいない時に、店長がパスキーを全部なくした場合だけ使う。
- Supabase のダッシュボードの SQL で、パスキーを全部消し、**役割を止め**、合言葉を作ってメールを出す（窓は、リンクを押した時にアプリが開ける。手順は `docs/06_Operations/` に新しく書く）。
- 手順書には「パスキーを2本以上、別々の端末に持つ」ことを先に書く。

**ログインの長さ（24時間・1時間）**

- 無料のプランには Supabase の時間の制限が無い（確定。Pro 以上）。だからアプリと DB で守る。
- 基準に `public.sessions` の行の作られた時刻は使えない。今の `persistNewSession` は、トークンを更新するたびに新しい行を作り、古い行を失効させるので、行の時刻は約1時間ごとに新しくなる。基準は GoTrue のセッション（`session_id`）の側に置く。
- 24時間: `amr` の `passkey` の時刻（ログインの時刻。更新しても変わらない。T2 で確かめた）から24時間。フック（5-2）がそれを超えた更新を拒否する。拒否は GoTrue のセッションを終わらせないので、セッションの生死だけでは切れない（5-2）。管理の入口の判定（5-2 の2つ目）も、同じ時刻で API と RLS を止める（アクセストークンの期限が残っていても止まる）。
- 1時間: GoTrue のセッション（`session_id`）ごとに「最後に使った時刻」を持つ（`auth.sessions.refreshed_at` か、`session_id` ごとのアプリの表。作り手が選ぶ）。認証の通った要求で更新し（書き込みは数分に1回に間引く）、1時間を超えたら API と RLS を止める。
- 切れたら、画面は `/login` に送る。

**Google**

- 店員の Google は使えない（フックで拒否）。Google の窓口でも、店員なら「店員はパスキーで」と出す。

**認証アプリ（TOTP）**

- 窓口・画面（`/auth/verified`、`/api/auth/mfa/*`）を消す。手元の config と本番の設定で TOTP を止める。
- 今ある店員の TOTP の要素は、移す時に全部消す。残すと、パスキーの登録と削除に `aal2` を求められて止まる（確定。GoTrue の決まり）。

## 7. 消すもの・残すもの

| 区分 | もの |
| --- | --- |
| 消す | パスワードのログイン・登録・再設定・変更の画面と窓口、`passwordSchema`、漏洩パスワードの照合（ADR-0405）、`password_reset_tokens`・`password_change_challenges` の表と関数、`/auth/verified` と `/api/auth/mfa/*`、`/admin/create-user` |
| 作り直す | ログインの画面、メールのコードの保留（ADR-0400〜0402）、`/api/auth/me` の `mfaVerified`（意味を「パスキーで入った店員か」に変える。応答の形は保つ。80本の E2E がこの形を偽装しているため）、MFA のやり直しの窓口（ADR-0457）、captcha の扱い（ADR-0420） |
| 残す | 結び付け（ADR-0417・0419）、refresh・logout・戻り先（ADR-0406・0407・0412・0413）、no-store・IP・CSRF（ADR-0415・0416）、監査（ADR-0460〜0462）、回数の制限 |
| 新しく作る | フック、パスキーのサーバーの窓口（ログインの始め・終わり、登録の始め・終わり、一覧・名前・削除）、招待とやり直しの合言葉、登録の窓の表、認めたパスキーの表、知らせ、店員の24時間・1時間、店長の最後の手段の手順書 |

ADR は、置き換わる物（0400・0403・0405・0421 と、0409・0418 の aal2 の部分）に「置き換え済み」と書き、新しい ADR を足す（パスキーで入ったかで判定する、フックで店員を締める、UV を必須にする、など）。

## 8. データ・移す時・本番

### 8-1 今いる人

- 本番のアプリはまだ公開していない。本番の DB にいるのは試し用の4人だけ（残すと決めてある）。
- その人たちのパスワードは使えなくなる（フックが拒否）。店員がいれば、段3の後に店長の招待かやり直しで入り直す。
- 店員の TOTP の要素は、移す時に全部消す（6-2）。

### 8-2 本番で要ること

- パスキーの RP ID（パスキーが結び付く住所）は、本番の独自のドメインに決める。後から変えると全員のパスキーが使えなくなる（確定）。だから本番の住所が決まるまで、本番のパスキーは有効にしない（captcha の段階 B と同じ待ち）。
- ダッシュボードで: Passkeys の有効化と RP の設定、Custom Access Token フックの登録、TOTP を止める。手順は `docs/06_Operations/supabase-auth-config.md` に足す。
- **本番で確かめること（手元の試しで測れなかった物。2026-11-16。[結果の文書](2026-11-16-passkey-local-trial-results.md)の「本番の確認（8-2）に回す未確認」）**:
  1. T7: 本番のホスト版で、パスキーのログインの始めの回数の制限が効くか。管理者の鍵・`sb_secret_` で免除されるか。**`Sb-Forwarded-For` にお客さんの IP を入れた時に、その IP ごとに数えるか**（効かなければ 5-1 の (b) に切り替える）。この添え書きは `sb_secret_` でだけ受け付けられ、プロジェクトの設定で有効にする必要がある。有効にする運用の手順は、段1で `docs/06_Operations/supabase-auth-config.md` に書く。**この確認は、本番の独自のドメインが決まってから行う**（オーナーが2026-11-16 に決定。確認は本番でパスキーを有効にした後にしかできないので、仮の住所では有効にしない）。効かなくても、(b) への切り替えは設定の変更だけで済む（5-1。(b) は段1で作っておく）。確認では、鍵の形（`sb_secret_`）も確かめる。
  2. T7: `sb_secret_` が、本番でも captcha を免除されるか（手元では免除された）。免除されないと、今のサーバーの認証の道（ADR-0420 のサーバーからの認証、メールのコードの送りなど）も止まる。その時は、これらにも同じ形でトークンを渡す直しが要る。
  3. T5: GoTrue の更新で引き金が消されないか。本番の `auth` の表に `postgres` で引き金を作れるか。
  4. T4: PIN の無い物理キーでの挙動（UV の印、一覧を渡さないログイン）。**開店前に足す確認**。
  5. T2: 本物の Google ログイン（`oauth`）の `amr` と、フックの拒否。本番の独自のドメインが決まった後に、本物で確かめる。
  6. 本番でパスキーを使えるか（無料のプランでダッシュボードの「Passkeys」を有効にできるか。4-1 と同じ）。
  7. 本番の GoTrue の版が v2.196.0 か。違えば、試し T1〜T7 の前提を見直す。
  8. T7: 古い形の `service_role` の鍵も、本番で captcha を免除されるか（上の 2 は `sb_secret_` だけ）。
  9. T2: 本番のフックの登録後に、拒否の応答の形（403・`unknown`・フックの文）が手元と同じか（アプリは文で「店員はパスキーで」と見分ける）。
- 2026-11-06 に書いたダッシュボードの手順のうち、パスワードの欄（最小16字など）はパスキーに移れば要らなくなる。メールのコード（8桁・5分）と文面の手順は、引き続き要る。

## 9. 試験の方針

- パスキーの E2E は、Playwright の仮想の認証器（Chromium の CDP の `WebAuthn.addVirtualAuthenticator`、UV あり）で、本物の登録とログインを流す。UV の無い仮想の認証器は、Chromium では一覧を渡さないログインに答えられないので、UV 無しを断る E2E では使う鍵の一覧（`allowCredentials`）を足す（T4）。
- 会員のログインの手助け（`loginAsMember`。17本が使う）は、メールのコードの流れ（Mailpit から読む）に作り直す。
- 管理の手助け（`createAdminSessionActor`。17本が使う）は、今はパスワードで JWT を作っている。フックがあると店員はパスキー以外で入れないので、Node の中で動くソフトの認証器（鍵の対を作り、署名を作る）でパスキーの JWT を作る形に作り直す。作り方は作り手に任せる。
- `/api/auth/me` を偽装する約80本は、応答の形を保てばそのまま通る。
- 新しい E2E は、決まり（`e2e/FR-LOGIN-NNN-*.spec.ts` などの名前、390・768・1280 の3つの幅）に従う。
- 消す画面の E2E（FR-PWRESET の10本、FR-LOGIN の TOTP とパスワードの分、FR-ACCOUNT-046 など）は、消す段で消す。

## 10. 危険と、残る心配

| 心配 | どうするか |
| --- | --- |
| Supabase のパスキーはベータ版。API が予告なく変わる | 版を固定する。上げる時は E2E を全部流す |
| Supabase のパスキーが止まると、店員はだれも入れない（予備が無い） | オーナーの決定（店員に予備なし）の結果として受け入れる。お客さんはメールのコードで入れるので、注文は止まらない。発送などの作業は直るまで止まる。急ぎは Supabase のダッシュボードで行う |
| 無料のプランで本番のパスキーが有効にできない | 有力では使える。本番の住所が決まった時に最初に確かめる。だめなら、その時にオーナーに戻る |
| フックが壊れると、全員のログインが止まる | フックは短く保ち、手元の DB の試験で全部の分岐を確かめる |
| GoTrue を直に叩いて、店員のパスキーを消される・足される | 足すにはパスキーで入ったセッションが要る（フックで締める）。直に足した鍵は認めたパスキーに入らないので、店員としては入れない（5-5）。足し・消しは DB の側で拾って知らせる |
| 始めの回数の制限（IP ごとに5分30回。上げる設定は無い＝確定、ホスト版で変えられない＝有力）で、店全体が入れなくなる | 始めをサーバーから `sb_secret_` と `Sb-Forwarded-For` で呼び、お客さんごとに数える（5-1 の (a)）。本番で添え書きが効かなければ、ブラウザから直に呼ぶ道（(b)）に切り替える。本番で確かめる（8-2） |
| 引き金で拾えない道がある（`TRUNCATE`、`DISABLE TRIGGER`、`session_replication_role = replica`。強い権限の人だけ） | 残る危険として受け入れる。本番の DB に強い権限で入れる人は限られる。GoTrue の更新で引き金が消えないかを 8-2 で確かめる |
| UV の確かめをソフトの認証器でしか試していない | 守りの本体はサーバーの門（UV の印が無ければ拒否）なので崩れない。PIN の無い物理キーでの確認を開店前に足す（8-2） |
| 本物の Google ログインを試していない | 店員は「パスキー（と窓）以外は全部断る」作りなので、`amr` の形が違っても店員は通らない。危険は小さい。本番の住所が決まった後に本物で確かめる（8-2） |
| GoTrue はパスキーの回数の逆戻り（複製）を検知しない（有力） | 複製された鍵は検知できない。知らせ（5-4）と、店員の24時間・1時間の上限で被害を狭める |
| 店員のメールが乗っ取られた時に、やり直しのメールで入られる | やり直しは店長しか出せない。出したら店長と本人に知らせる。期限24時間・使い切り |

## 11. 作り手に任せること

- フックの SQL の書き方と、`supabase_auth_admin` に渡す権限
- パスキーの足し・消しを DB で拾う引き金の書き方（引き金で拾うことは決まった。5-4。更新のどれを知らせるかの切り分けの実装は任せる）
- 合言葉の作り方（今の再設定の合言葉と同じ作り：SHA-256 で保存・使い切り）
- 管理の手助けの、ソフトの認証器の作り方
- 画面の細かい見た目（今のブランドの見た目に合わせる）
- 文書の ID の振り方（`documentation-guide` スキルに従う）

## 12. 私（設計した者）の判断の一覧

オーナーが決めたことではなく、私が決めたこと。違えば直す。

1. 新規のお客さんも「メール → コード」で作る（登録の画面とパスワードを無くす）
2. パスキーのログインは、ボタンを押してから始める（画面を開いた時の自動の候補は使わない）。Turnstile は付けない（始めをサーバーから `sb_secret_` で呼ぶ道に決まった。12-2 の2）。本番で添え書きが効かない時だけ、ブラウザから直に呼び、見えない形で付ける
3. UV（顔・指紋・PIN）を全員に必須にする
4. コードで入るたびに「パスキーを作る」を勧める
5. 招待とやり直しのリンクの期限は24時間
6. 1本しか無い店員は、2本目を登録するまで管理の権限が無い（画面・API・RLS のすべて）
7. 知らせの遅れは数分まで許す
8. 店長が作れるのは店員だけ（お客さんを店長が作る機能は無くす）
9. 店員のパスキーは、アプリで登録した物だけ有効。足す前に5分以内のパスキーでの入り直しを求める（5-5）
