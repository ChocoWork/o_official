# ログインをパスキーに置き換える 設計書

> 対象: ログイン・会員登録・店員（店長とサポーター）の本人確認・アカウントの守り（AUTH 領域の全部）
> 関連: [本番の Auth の設定](../../06_Operations/supabase-auth-config.md)、[AUTH の要求](../../02_Requirements/areas/auth.md)、[AUTH の基本設計](../../03_BasicDesign/areas/auth.md)、[AUTH の脅威](../../05_Quality/security/threats/auth.md)
> 確認日: 2026-11-07。オーナーとの会話（2026-11-06〜07）で決めた内容と、調べ（2026-11-06〜07）の結果を書く

---

## 概要

お客さん・サポーター・店長の全員を、パスワードからパスキーに置き換える。パスワードはなくす。

| 項目 | 内容 |
| --- | --- |
| なぜ | パスワードは、盗まれる・使い回される・だましのページで抜かれるのが一番多い入口。パスキーは端末の鍵で入るので、だましのページでは使えない。NIST・OWASP ともに一番強い方法として挙げている |
| お客さん | パスキーで入る。予備はメールに届く8桁のコード。Google でも入れる。コードで入ったらパスキーを作るように勧める |
| 店員（店長・サポーター。同じ扱い） | パスキーだけで入る。2本以上を持つ。メールのコード・Google・パスワード・認証アプリでは入れない |
| 店員のやり直し | パスキーを全部なくした店員は、店長がやり直しの手続きを出す。店長本人の最後の手段は Supabase のダッシュボード |
| 店員のログインの長さ | 入ってから最長24時間。何もしないで1時間たったら入り直し |
| 知らせ | パスキーを足した・消したら、本人にメールで知らせる。店員の場合は店長にも知らせる |
| 使う物 | Supabase のパスキー（ベータ版）。`@supabase/supabase-js` を 2.117.0 以上へ上げる |
| 一番大事な仕組み | 店員のログインの状態は、パスキーで入った時だけ作られる。これを Supabase の「トークンを出す前の確かめ」（Custom Access Token フック）1か所で締める。店員のパスキーは、アプリの窓口で登録した物だけを有効にする（5-5） |
| 順番 | 最初に手元で試し（4-1）。試しで前提が崩れたら、作る前にオーナーに戻る |

---

## 1. 目的と、しないこと

### 1-1 目的

- だましのページ・パスワードの使い回し・パスワードの総当たりで、アカウントを取られないようにする
- 店員のアカウントは、パスキー以外のどの道からも入れないようにする（管理画面は注文・返金・お客さんの住所を扱うため）
- お客さんは、パスキーが無くてもメールのコードか Google で入れるようにする（手軽さを落とさない）

### 1-2 しないこと

- お客さんのログインの長さは変えない（今と同じ。7日間、使うたびに延びる）
- 決済・カート・お気に入り・ゲストの注文の仕組みは変えない
- 権限（だれが何をできるか）の表と割り当ては変えない
- 店員の Google Workspace によるログイン（会社が配る Google アカウント）は入れない。今は店員が数人なので、パスキーだけのほうが簡単で強い
- お客さんの Shop Pay のような外のサービスのパスキーは使わない

### 1-3 失敗とみなすこと

- 店員が、メールのコード・Google・パスワード・やり直しのメールのどれかだけで管理画面に入れる
- 店員のアカウントに、本人も店長も知らないうちにパスキーが足される
- 店員が全員パスキーをなくして、ダッシュボードの手順でも戻れない
- お客さんが、パスキーを作らないと買い物できない
- 試験（E2E）が手元の Supabase で流せなくなる

## 2. 基準と、ほかの所との比べ

調べた日は 2026-11-06〜07。

### 2-1 NIST・OWASP

| 項目 | NIST SP 800-63B-4 | OWASP | この設計 |
| --- | --- | --- | --- |
| だましに強い方法 | AAL2 では、だましに強い方法を選べるようにする（SHALL） | FIDO2/WebAuthn を一番に勧める | 全員がパスキーを使える。店員はパスキーだけ |
| パスキーを「2要素」と数える条件 | 端末で本人確認（顔・指紋・PIN）をした印（UV）がある時だけ。無ければ1要素 | 同じ考え | 全員、UV の印を必須にする（5-3） |
| メールのコード | 本人確認の手段に使ってはならない（SHALL NOT） | 弱い。ASVS L3 は認証に使わない | 店員には使わない。お客さんの予備としてだけ使う（Shopify と同じ） |
| コードの長さ・期限 | 6桁以上・10分以内 | 20ビット以上・10分以内 | 8桁・5分（今のまま） |
| ログインの長さ（AAL2） | 全体24時間以内・無操作1時間以内（SHOULD） | 事務用は全体4〜8時間・無操作15〜30分が目安 | 店員は24時間・1時間（NIST の上限）。オーナーの決定 |
| 管理者の多要素 | — | 管理者には必ず求める | 店員はパスキーだけで入る。UV の印で2要素にする |
| やり直し | — | やり直しで多要素を飛ばせてはならない。要素の変更は危険度が高い操作 | 店員のやり直しは店長だけが出せる。足す・消すは知らせる |

出典: [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b/)、[NIST の同期型パスキー](https://pages.nist.gov/800-63-4/sp800-63b/syncable/)、[NIST のセッション](https://pages.nist.gov/800-63-4/sp800-63b/session/)、[OWASP ASVS 5.0](https://owasp.org/www-project-application-security-verification-standard/)、[OWASP MFA Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)、[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## 3. オーナーが決めたこと（2026-11-06〜07）

1. 全員パスキーにする。パスワードはなくす
2. お客さん: パスキーで入る。予備はメールの8桁のコード。コードで入ったらパスキーを作るように勧める。Google は残す。パスキーを足した・消したらメールで知らせる。ログインの長さは今のまま
3. 店員（店長・サポーターは同じ扱い）: パスキーだけ。2本以上。メールの予備は無し
4. 店員のやり直しは店長が出す。店長本人の最後の手段は Supabase のダッシュボード
5. 店員のログインは最長24時間・無操作1時間
6. 店員のパスキーを足した・消したら、本人と店長に知らせる
7. 店員の認証アプリ（TOTP）と Google はなくす
8. Supabase のパスキー（ベータ版）を使う。supabase-js を上げる

## 4. 進め方

### 4-1 最初に手元で試す（作り始める前の関門）

調べはソースと文書を読んだ結果で、手元ではまだ動かしていない。次の6つを手元の Supabase（CLI の GoTrue v2.196.0）で確かめてから作り始める。試しの道具は捨てる前提で作る。

| # | 確かめること | 崩れたら |
| --- | --- | --- |
| T1 | パスキーの登録とログインが手元で動き、JWT が `aal1`・`amr` に `passkey` を持つ | 作り方を見直す。オーナーに戻る |
| T2 | Custom Access Token フックで、店員の「パスキー以外のログイン」と「24時間を超えた更新」を拒否できる（ログイン時と更新時の両方） | 店員の締め付けを別の方法（5-2 の予備）で組む。オーナーに戻る |
| T3 | RLS の中で `auth.jwt()` の `amr` が読め、`passkey` かを判定できる | フックで独自の印を JWT に足して、それを読む |
| T4 | ブラウザに渡す選択肢で UV を「必須」にでき、届いた結果の UV の印をサーバーで読める（5-3） | UV の確かめはあきらめ、危険として残す。オーナーに戻る |
| T5 | パスキーの追加・削除を、どの道から行われても DB の側で拾える（`auth.webauthn_credentials` への引き金か、`auth.audit_log_entries` を定期的に読む） | 拾える範囲だけ知らせる。残りは危険として残す |
| T6 | 招待のセッション（アプリが `admin.generateLink` の magiclink を作ってすぐ検証したもの）で、パスキーを2本登録できる。フックの入力にそのセッションの `session_id` が入り、窓（6-2）の行の `session_id` と突き合わせられる | 招待の流れ（6-2）を組み直す |
| T7 | パスキーのログインの始め（`/passkeys/authentication/options`）の回数の制限（IP ごとに5分30回）が、サービスの鍵の呼び出しで免除されるか | 免除されないなら、始めはブラウザから GoTrue を直に呼ぶ（5-1） |

本番でパスキーを使えるかは、無料のプランでダッシュボードの「Passkeys」を有効にできるかで決まる（有力。料金表にパスキーの行が無い）。これは本番の住所（独自のドメイン）が決まってから確かめる（8-2）。

### 4-2 作る段

1つの計画にまとめず、段ごとに計画を分ける。各段は単独で試験が通る。

| 段 | 中身 |
| --- | --- |
| 段1 土台 | supabase-js・`@supabase/ssr` を上げる。手元の config を変える。フック。`has_permission` と管理の入口の判定を「パスキーで入ったか」へ。パスキーの登録・ログインのサーバーの窓口 |
| 段2 お客さん | ログインの画面、メールのコードの流れ（新規も同じ流れ）、パスキーを勧める画面、アカウントのパスキーの一覧、知らせ |
| 段3 店員 | 招待、2本の登録、やり直し、24時間・1時間、Google の拒否、店長への知らせ、店長の最後の手段の手順書 |
| 段4 片付け | パスワード・認証アプリの画面・窓口・表・試験を消す。文書の正本を直す |

### 4-3 本番の DB に当てる時

段1の移行（フックと、管理の入口の判定の変更）を本番に当てると、本番ではパスキーを有効にするまで、だれも管理の権限を持てない。お客さんのパスワードも使えなくなる。

- 2026-11-07 時点で、普段の開発（`npm run dev`）は本番の DB を向いている。このまま当てると、店長が開発の画面で管理画面に入れなくなる。
- だから本番に当てるのは、開発を手元の Supabase に切り替えた後にする（会計の前提として 2026-11-05 にオーナーが決めた切り替えと同じ物）。切り替えの前は、移行を本番に当てず、push もしない。
- 本番のアプリはまだ公開していないので、切り替えた後なら本番に当てても困る人はいない。

## 5. 全体の仕組み

### 5-1 ログインの状態は必ずアプリを通して作る

今の決まり（ADR-0417・0419: アプリが GoTrue のセッションを自分の Cookie と `public.sessions` の行に結び付け、結び付いていないセッションは API でも DB でも拒否）をそのまま守る。

- パスキーのログインは、低い層の API（`passkey.startAuthentication` → ブラウザの WebAuthn → `passkey.verifyAuthentication`）を使う。
  - 終わり（検証）は、必ずアプリのサーバーの窓口を通す。
  - 始め（選択肢を取る）は、T7 で決める。GoTrue の回数の制限（IP ごとに5分30回。設定で変えられない）が、サーバーの呼び出しで免除されないなら、全員の要求がサーバーの1つの IP から出て、店全体で5分30回しか入れなくなる。その時は、ブラウザから GoTrue を直に呼ぶ。GoTrue の captcha が有効なら Turnstile のトークンを付ける（見えない形の Turnstile を使う）。
  - ブラウザは鍵の操作だけをする。
- 検証に通ったら、今の `persistSessionAndCookies()` で結び付けを書く。
- 登録も、アプリのサーバーの窓口を通す（ログイン中の本人のトークンで GoTrue を呼ぶ）。

### 5-2 店員の締め付け（フック）

Custom Access Token フック（Postgres の関数。無料のプランで使える）を1つ置く。トークンを出す時（ログイン時と更新時）に毎回走る。

| 相手 | `amr` の中身 | 結果 |
| --- | --- | --- |
| 店員（`user_roles` で有効な admin・supporter） | `passkey` があり、そのログインから24時間以内 | 出す。アプリが認めたパスキー（5-5）が2本以上あるかを独自の印として JWT に入れる |
| 店員 | 店長が開けた「登録の窓」（6-2）が開いていて、そのセッションの `session_id` が窓の行に控えた物と同じ | 出す（パスキーの登録しかできない。管理の権限は無い） |
| 店員 | それ以外（`otp`・`oauth`・`password`、24時間を超えた `passkey`、窓が閉じた招待） | 拒否 |
| お客さん | `password` | 拒否（パスワードは廃止。アプリには入口が無いが、GoTrue を直に叩く道を閉じる） |
| お客さん | それ以外 | 出す（今のまま） |

これで、メールのコード・Google・パスワード・GoTrue の直叩きのどれでも、店員のログインの状態は作れない。Google の自動のつなぎ（同じ確認済みメールの Google を同じアカウントにつなぐ。Supabase の仕様で止められない）が起きても、店員としてのトークンは出ない。

- 予備（T2 で崩れた時）: アプリの結び付け（5-1）で店員のパスキー以外の結び付けを書かず、`private.app_session_is_live` で店員のパスキー以外を拒否する。この場合 GoTrue を直に叩けばトークンは出るが、API と RLS は通らない。
- 窓はセッションの `session_id` に結ぶ。ユーザーだけに結ぶと、窓が開いている24時間は、店員のふだんのメールのコードでもトークンが出てしまうため。
- 管理の入口の判定を変える。今は「`aal` が `aal2` か」を見ている（アプリは `admin-rbac.ts`、DB は `has_permission`）。これを次の3つ全部に変える。結び付き（ADR-0418 の後半）はそのまま。
  1. `amr` に `passkey` がある
  2. そのパスキーのログインの時刻から24時間以内（6-2）
  3. フックが入れた「認めたパスキーが2本以上」の印がある（6-2 の「1本しか無い店員」を API と RLS でも止めるため）

### 5-3 顔・指紋・PIN の確かめ（UV）を必須にする

Supabase はパスキーの UV を「あれば使う」（preferred）にしていて、PIN の無い物理キーでも通る（確定。ソースで確認）。NIST の考えでは、UV が無いパスキーは1要素にすぎない。

- アプリの始めの窓口で、ブラウザに渡す選択肢の `userVerification` を `required` に書き換える。
- 終わりの窓口で、届いた `authenticatorData` の UV の印（flags の 0x04）を読み、無ければ GoTrue に渡す前に拒否する。
- 印は GoTrue が署名を確かめる同じバイト列なので、書き換えれば GoTrue の検証で落ちる。だからアプリの読み取りは信用できる（T4 で確かめる）。
- 登録の時も同じく UV を必須にする。
- 全員に適用する（スマホ・PC のパスキーは、いつも顔・指紋・PIN を求めるので、お客さんの手間は増えない）。
- この確かめは、ログインの状態を必ずアプリを通して作る決まり（5-1、ADR-0417・0419）に頼っている。GoTrue を直に呼べば UV の無いパスキーのセッションは作れるが、アプリに結び付かないので API でも RLS でも使えない。結び付けの旗（`AUTH_REQUIRE_APP_SESSION`）を切ると、UV の必須も効かなくなる。このことを新しい ADR に書く。

### 5-4 パスキーの足し・消しの知らせ

GoTrue には、パスキーの通知もフックも無い（確定）。アプリの窓口だけで知らせると、GoTrue を直に叩いた足し・消しを見落とす。

- DB の側で拾う（T5 で決めた方法）。拾った足し・消しを、今の注文メールと同じ「送る予定の表」（outbox）に積み、アプリが送る。
- 宛先: お客さんは本人。店員は本人と、有効な店長（admin）全員。
- 文面: 「パスキーが追加されました（名前・日時）。心当たりが無ければ、すぐに店長へ」など。お客さん向けと店員向けで分ける。
- 遅れは数分まで許す（私の判断）。

### 5-5 店員のパスキーは、アプリで登録した物だけ有効にする

盗まれたセッションのままパスキーを足されると、24時間の上限を越えて入り続けられてしまう。GoTrue の登録の窓口は、ログイン中なら直に叩けるので、アプリの画面で止めるだけでは足りない。

- 店員がアプリの窓口でパスキーを登録したら、その鍵の ID をアプリの表（`private` の下）に控える。これを「認めたパスキー」と呼ぶ。
- 店員がパスキーで入る時、アプリの終わりの窓口は、届いた鍵の ID が認めたパスキーの表にあるかを確かめる。無ければ拒否する。GoTrue を直に叩いて足したパスキーでは、店員としては入れない。
- 店員がアプリの窓口でパスキーを足す時は、直前（5分以内）にパスキーで入り直したことを求める（OWASP の「要素の変更は危険度が高い操作」）。登録の窓（6-2）の中の最初の2本は除く。
- 認めたパスキーの本数（2本以上か）は、この表で数える。フックはこの表を読んで印を JWT に入れる（5-2）。
- GoTrue を直に叩いて足された鍵は、知らせ（5-4）で店員と店長に届く。
- お客さんには、この表を使わない。お客さんがパスキーを足す時は、直前（10分以内）にパスキーかメールのコードで入ったことを、アプリの窓口で求める（私の判断）。

## 6. 流れ

### 6-1 お客さん

**ログイン（`/login`）**

- 「パスキーでログイン」のボタン、「Google でログイン」のボタン、「メールでコードを受け取る」の入口を並べる。
- パスキーはボタンを押してから始める。画面を開いた時の自動の候補（conditional UI）は使わない。選択肢の期限（5分）が切れやすく、captcha とも合わないため（私の判断）。
- パスキーのログインの Turnstile は T7 で決める。始めをサーバーから呼べるなら付けない（鍵が無ければ通らないので、ボットの対策は窓口の回数の制限で足りる。GoTrue の captcha は今と同じくサービスの鍵の呼び出しで免除。ADR-0420）。ブラウザから直に呼ぶなら、GoTrue の captcha のために見えない形の Turnstile を付ける（私の判断）。

**メールのコード（予備と新規の両方）**

- メールアドレスを入れる → Turnstile → 8桁のコード（5分）→ 入れる → ログイン。
- 登録が無いアドレスなら、この流れでアカウントを作る（Shopify と同じ。登録の画面とパスワードを無くす。私の判断）。今の登録の画面にパスワード以外の欄（同意など）があれば、この流れに移す。
- 登録済みかどうかで、画面も応答も変えない（列挙対策。今の SEC-AUTH-016 を保つ）。
- 今の「保留の Cookie・再送・総当たりの制限」（ADR-0400〜0402）は、コードの段だけに作り直して使う。

**コードで入った後**

- パスキーが1本も無ければ、「パスキーを作る / あとで」の画面を出す。コードで入るたびに出す（私の判断）。
- 作る時は UV 必須（5-3）。名前は端末名を初期値にする。

**アカウントの画面**

- パスキーの一覧（名前・作った日）。名前の変更・削除・追加。
- 最後の1本も消せる（メールのコードが残るため）。
- 今の `/account/password` は消す。

**Google**

- 今のまま。コードを求めない（今の挙動。未決だった SEC-AUTH-008 は「お客さんの Google はコード無し」で閉じる）。

### 6-2 店員

**招待（新しい店員）**

1. 店長が管理画面の「ユーザー」で、メールと役割（店長・サポーター）を入れて招待する。今の `/admin/create-user`（パスワードを直に入れる）は消す。
   - アドレスにアカウントが無ければ、パスワードの無いアカウントを作る。
   - すでにお客さんのアカウントがあれば、そのアカウントに役割を付ける。GoTrue の招待（`inviteUserByEmail`）は確認済みのアドレスを断るので使わない。
2. アプリが使い切りの招待の合言葉を作り、メールで送る。期限は24時間（私の判断）。GoTrue のメールのリンクはコードと同じ5分で切れるので、そのままは使えない。
3. 店員がリンクを押す。アプリが合言葉を確かめ、その場で GoTrue のセッションを作る（`admin.generateLink` の magiclink を作って、サーバーですぐ検証する）。同時に「登録の窓」を開ける（`private` の表に、だれの・どのセッションの・いつまでの窓かを置く）。
4. 店員は登録の画面で、パスキーを2本登録する。別の端末かセキュリティキーを勧める。2本とも認めたパスキー（5-5）に控える。
5. 2本そろったら、窓を閉じ、そのセッションを終わらせ、パスキーでのログインに送る（そのセッションの `amr` は `magiclink` のままで、`passkey` は付かないため）。

**今いる人を店員に上げる時**

- 今の「ユーザー」の役割の変更（`PATCH /api/admin/users`）で、お客さん（`user`）を店長・サポーターに上げることは、今も残す。
- ただし上げる時は、必ずやり直し（下）と同じことをする。その人のパスキーを全部消し、ログインを全部終わらせ、合言葉のメールを出し、窓を開ける。お客さんとして作ったパスキーや、自動でつながった Google を、店員の入口として持ち越さないため。
- 店員からお客さんに下げる時は、認めたパスキーの表からその人の行を消し、ログインを全部終わらせる。

**ふだんのログイン**

- お客さんと同じ `/login` の「パスキーでログイン」を使う。入った後、店員は管理画面へ。
- 店員がメールのコードや Google を試したら、「店員はパスキーでログインしてください」と出す（フックで拒否された応答を、アプリがこの文に直す）。

**パスキーの管理**

- 自分のパスキーの一覧・追加・名前の変更・削除。
- 削除で2本を切る時は、画面で止める。GoTrue を直に叩かれると止められないので、知らせ（5-4）で気づけるようにする。直に消された鍵は、認めたパスキーの表からも消す（5-4 で拾った時）。
- 認めたパスキーが1本しか無い店員がパスキーで入ったら、「もう1本登録してください」の画面に送る。管理の権限は、画面だけでなく API と RLS でも無い（5-2 の3つ目の条件。私の判断）。

**やり直し（パスキーを全部なくした店員）**

1. 店長が「ユーザー」で、その店員の「パスキーを全部消してやり直す」を押す。確認の語と理由（10〜500字）を入れる（今の MFA のやり直し ADR-0457・0461 と同じ守り。今は画面が無いので作る）。
2. アプリがその店員のパスキーを全部消し、ログインを全部終わらせ、招待と同じ合言葉のメールを送り、窓を開ける。
3. 後は招待の 3〜5 と同じ。
4. 自分自身のやり直しはできない（今と同じ）。

**店長本人の最後の手段**

- ほかに店長がいない時に、店長がパスキーを全部なくした場合だけ使う。
- Supabase のダッシュボードの SQL で窓を開け、合言葉のメールを出す（手順は `docs/06_Operations/` に新しく書く）。
- 手順書には「パスキーを2本以上、別々の端末に持つ」ことを先に書く。

**ログインの長さ（24時間・1時間）**

- 無料のプランには Supabase の時間の制限が無い（確定。Pro 以上）。だからアプリと DB で守る。
- 基準に `public.sessions` の行の作られた時刻は使えない。今の `persistNewSession` は、トークンを更新するたびに新しい行を作り、古い行を失効させるので、行の時刻は約1時間ごとに新しくなる。基準は GoTrue のセッション（`session_id`）の側に置く。
- 24時間: `amr` の `passkey` の時刻（ログインの時刻。更新しても変わらない）から24時間。フック（5-2）がそれを超えた更新を拒否する。管理の入口の判定（5-2 の2つ目）も、同じ時刻で API と RLS を止める（アクセストークンの期限が残っていても止まる）。
- 1時間: GoTrue のセッション（`session_id`）ごとに「最後に使った時刻」を持つ（`auth.sessions.refreshed_at` か、`session_id` ごとのアプリの表。作り手が選ぶ）。認証の通った要求で更新し（書き込みは数分に1回に間引く）、1時間を超えたら API と RLS を止める。
- 切れたら、画面は `/login` に送る。

**Google**

- 店員の Google は使えない（フックで拒否）。Google の窓口でも、店員なら「店員はパスキーで」と出す。

**認証アプリ（TOTP）**

- 窓口・画面（`/auth/verified`、`/api/auth/mfa/*`）を消す。手元の config と本番の設定で TOTP を止める。
- 今ある店員の TOTP の要素は、移す時に全部消す。残すと、パスキーの登録と削除に `aal2` を求められて止まる（確定。GoTrue の決まり）。

## 7. 消すもの・残すもの

| 区分 | もの |
| --- | --- |
| 消す | パスワードのログイン・登録・再設定・変更の画面と窓口、`passwordSchema`、漏洩パスワードの照合（ADR-0405）、`password_reset_tokens`・`password_change_challenges` の表と関数、`/auth/verified` と `/api/auth/mfa/*`、`/admin/create-user` |
| 作り直す | ログインの画面、メールのコードの保留（ADR-0400〜0402）、`/api/auth/me` の `mfaVerified`（意味を「パスキーで入った店員か」に変える。応答の形は保つ。80本の E2E がこの形を偽装しているため）、MFA のやり直しの窓口（ADR-0457）、captcha の扱い（ADR-0420） |
| 残す | 結び付け（ADR-0417・0419）、refresh・logout・戻り先（ADR-0406・0407・0412・0413）、no-store・IP・CSRF（ADR-0415・0416）、監査（ADR-0460〜0462）、回数の制限 |
| 新しく作る | フック、パスキーのサーバーの窓口（ログインの始め・終わり、登録の始め・終わり、一覧・名前・削除）、招待とやり直しの合言葉、登録の窓の表、認めたパスキーの表、知らせ、店員の24時間・1時間、店長の最後の手段の手順書 |

ADR は、置き換わる物（0400・0403・0405・0421 と、0409・0418 の aal2 の部分）に「置き換え済み」と書き、新しい ADR を足す（パスキーで入ったかで判定する、フックで店員を締める、UV を必須にする、など）。

## 8. データ・移す時・本番

### 8-1 今いる人

- 本番のアプリはまだ公開していない。本番の DB にいるのは試し用の4人だけ（残すと決めてある）。
- その人たちのパスワードは使えなくなる（フックが拒否）。店員がいれば、段3の後に店長の招待かやり直しで入り直す。
- 店員の TOTP の要素は、移す時に全部消す（6-2）。

### 8-2 本番で要ること

- パスキーの RP ID（パスキーが結び付く住所）は、本番の独自のドメインに決める。後から変えると全員のパスキーが使えなくなる（確定）。だから本番の住所が決まるまで、本番のパスキーは有効にしない（captcha の段階 B と同じ待ち）。
- ダッシュボードで: Passkeys の有効化と RP の設定、Custom Access Token フックの登録、TOTP を止める。手順は `docs/06_Operations/supabase-auth-config.md` に足す。
- 2026-11-06 に書いたダッシュボードの手順のうち、パスワードの欄（最小16字など）はパスキーに移れば要らなくなる。メールのコード（8桁・5分）と文面の手順は、引き続き要る。

## 9. 試験の方針

- パスキーの E2E は、Playwright の仮想の認証器（Chromium の CDP の `WebAuthn.addVirtualAuthenticator`、UV あり）で、本物の登録とログインを流す。
- 会員のログインの手助け（`loginAsMember`。17本が使う）は、メールのコードの流れ（Mailpit から読む）に作り直す。
- 管理の手助け（`createAdminSessionActor`。17本が使う）は、今はパスワードで JWT を作っている。フックがあると店員はパスキー以外で入れないので、Node の中で動くソフトの認証器（鍵の対を作り、署名を作る）でパスキーの JWT を作る形に作り直す。作り方は作り手に任せる。
- `/api/auth/me` を偽装する約80本は、応答の形を保てばそのまま通る。
- 新しい E2E は、決まり（`e2e/FR-LOGIN-NNN-*.spec.ts` などの名前、390・768・1280 の3つの幅）に従う。
- 消す画面の E2E（FR-PWRESET の10本、FR-LOGIN の TOTP とパスワードの分、FR-ACCOUNT-046 など）は、消す段で消す。

## 10. 危険と、残る心配

| 心配 | どうするか |
| --- | --- |
| Supabase のパスキーはベータ版。API が予告なく変わる | 版を固定する。上げる時は E2E を全部流す |
| Supabase のパスキーが止まると、店員はだれも入れない（予備が無い） | オーナーの決定（店員に予備なし）の結果として受け入れる。お客さんはメールのコードで入れるので、注文は止まらない。発送などの作業は直るまで止まる。急ぎは Supabase のダッシュボードで行う |
| 無料のプランで本番のパスキーが有効にできない | 有力では使える。本番の住所が決まった時に最初に確かめる。だめなら、その時にオーナーに戻る |
| フックが壊れると、全員のログインが止まる | フックは短く保ち、手元の DB の試験で全部の分岐を確かめる |
| GoTrue を直に叩いて、店員のパスキーを消される・足される | 足すにはパスキーで入ったセッションが要る（フックで締める）。直に足した鍵は認めたパスキーに入らないので、店員としては入れない（5-5）。足し・消しは DB の側で拾って知らせる |
| 店員のメールが乗っ取られた時に、やり直しのメールで入られる | やり直しは店長しか出せない。出したら店長と本人に知らせる。期限24時間・使い切り |

## 11. 作り手に任せること

- フックの SQL の書き方と、`supabase_auth_admin` に渡す権限
- パスキーの足し・消しを DB で拾う方法（引き金か、定期的な読み取りか。T5 の結果で決める）
- 合言葉の作り方（今の再設定の合言葉と同じ作り：SHA-256 で保存・使い切り）
- 管理の手助けの、ソフトの認証器の作り方
- 画面の細かい見た目（今のブランドの見た目に合わせる）
- 文書の ID の振り方（`documentation-guide` スキルに従う）

## 12. 私（設計した者）の判断の一覧

オーナーが決めたことではなく、私が決めたこと。違えば直す。

1. 新規のお客さんも「メール → コード」で作る（登録の画面とパスワードを無くす）
2. パスキーのログインは、ボタンを押してから始める（画面を開いた時の自動の候補は使わない）。Turnstile は、始めをサーバーから呼べるなら付けず、ブラウザから直に呼ぶなら見えない形で付ける（T7 で決まる）
3. UV（顔・指紋・PIN）を全員に必須にする
4. コードで入るたびに「パスキーを作る」を勧める
5. 招待とやり直しのリンクの期限は24時間
6. 1本しか無い店員は、2本目を登録するまで管理の権限が無い（画面・API・RLS のすべて）
7. 知らせの遅れは数分まで許す
8. 店長が作れるのは店員だけ（お客さんを店長が作る機能は無くす）
9. 店員のパスキーは、アプリで登録した物だけ有効。足す前に5分以内のパスキーでの入り直しを求める（5-5）
10. お客さんを店員に上げる時は、必ずやり直しと同じ手続きをする（パスキーを全部消して登録し直す）
11. 登録の窓は、ユーザーではなくセッションに結ぶ
12. お客さんがパスキーを足す時は、10分以内に入ったことを求める
13. 本番の DB に当てるのは、開発を手元の Supabase に切り替えた後（4-3）
