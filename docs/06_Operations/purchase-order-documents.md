# 取引書類（見積書・請求書の原本）の運用

> 状態: G-2 Task 8 の実装に基づく手順（本番へは未適用） | 確認日: 2026-10-25 | 対象: 発注書に添付する見積書・請求書の原本、非公開の入れ物 `purchase-order-documents`、`purchase_order_attachment_reservations` / `purchase_order_attachments` / `purchase_order_attachment_revisions`

## 概要

発注書の「取引書類」に保存した見積書・請求書の原本（PDF・JPEG・PNG、20 MiB まで）を、消さずに残し、訂正は追記で、検索と閲覧ができる形で運用するための手順をまとめる。保存は 予約 → 置き場へ直接 PUT → 確定 の二段階で、途中で止まっても続きから保存できる。この文書は、保存期間の方針、片側だけ失敗した時の見方と再開の手順、`sha256_source` の意味、署名つきリンクの扱いを定める。

| 項目 | 方針 |
| --- | --- |
| 保存期間 | 承認済みの[売上の計上の方針](../01_Planning/revenue-recognition-policy.md) 10章の7年を下限とし、アプリは自動で削除しない。起算点・延長・運用規程は同方針の税理士確認に従う（開店前に確認する） |
| 削除・上書き | 窓口にも DB の関数にも無い。予約・添付・版の3表は owner と service_role でも UPDATE・DELETE・TRUNCATE をトリガーが断る。置き場のファイルは `upsert: false` の署名つきの送り先でしか置けない |
| 訂正・無効化・差し替え | 次の版を追記する（理由が必須）。差し替えは新しい添付で、元の添付と版は変えない |
| ファイルの確かめ | ブラウザは送る前に、拡張子・ブラウザの種類・ファイルの先頭のバイト（PDF・JPEG・PNG の印）・20 MiB を確かめる。続きから保存で選び直したファイルは、予約の種類（保存キーの拡張子）の中身かを確かめる。サーバーは確定で置き場から読み戻し、同じ確かめと SHA-256 を行う |
| 差し替えの関係 | 差し替えの予約を作る時に、差し替える添付の id を予約の行に残す（その発注書の添付だけ）。確定は予約から版1へ写す。頁を読み直しても、続きから保存でも変わらない |
| 期限切れの予約 | 24時間を過ぎても自動で消えない。確認済みにして消す手段は無く、確定されるまで「保存が終わっていないファイル」に残り続ける（確定は期限後でもできる）。種類の検査に通らなかった予約も同じで、残り続ける |
| 置き場の WORM | 後続。アプリと DB が守るのは不変性までで、保存先の最高権限による変更・削除までは防げない |
| 署名つきリンク | 閲覧・ダウンロードは60秒。応答にだけ載せ、監査にもログにも画面の文にも出さない |

## 2. 保存の仕組みと、片側だけ失敗した時の見方

保存は DB の取引と置き場の書き込みを分けて行う（DB の取引の中で置き場を使わない）。予約は DB の1行、ファイルは置き場の1オブジェクトで、結び付けは保存キー `<発注書の id>/<乱数の uuid>.<拡張子>` と、確定が作る添付の行。どちらか片側だけが残る形は次のとおり。

| 状態 | 見え方 | 原因の例 | 手順 |
| --- | --- | --- | --- |
| 予約だけ（置き場にファイルが無い） | 発注書の頁の「保存が終わっていないファイル」 | 署名つきの送り先を作れなかった・PUT が失敗した・利用者が閉じた | 「続きから保存」で送り先を出し直し、ファイルを選び直して確定する。送り先を作れなかった後に同じ書類を保存し直すと、同じ要求番号で予約を再送するので同じ予約を受け取り、予約は増えない |
| 置き場にファイルがあり、添付が無い（DB 未確定） | 同上 | PUT の後の確定が失敗した（通信切れ・5xx・ハッシュの不一致） | 「続きから保存」。置き場に保存済みなので PUT は省かれ、確定だけが行われる |
| 置き場のファイルが種類の検査に通らない（拡張子と中身が合わない） | 確定が 422（`DOCUMENT_TYPE_UNSUPPORTED`）。画面は「このファイルは保存できませんでした。PDF・JPEG・PNG の正しいファイルを選び直して、新しく保存してください。」を出し、ファイルの選び直しを求める | ブラウザの確かめを通らない手段で置かれた・拡張子だけ付け替えたファイル。置き場のファイルは変えられない（`upsert: false`）ので、同じ予約はもう通らない | 画面の案内どおり正しいファイルを選び直す。新しい予約（新しい保存キー）で保存され、種類と差し替えの関係は止まった予約から引き継ぐ。止まった予約と置き場のファイルは消えず、「保存が終わっていないファイル」に残る（期限切れの確認の文つき。消す手段は無い）。その行の「続きから保存」を押しても同じ案内になる |
| 添付があり、応答だけ失った | 読み直すと添付済み | DB で確定した後の応答の喪失 | 何もしない。同じ内容なら同じ要求番号の再送が同じ結果を返し、別の要求番号は「この書類はすでに登録されています。」で二重にならない。画面は断られた後に発注書を読み直すので、保存が終わっていない一覧は添付済みの一覧に合う |
| 添付の行はあるが、置き場にファイルが無い | 「表示」「ダウンロード」「印刷」が「原本を取得できません。」（404 `DOCUMENT_NOT_FOUND`） | 置き場のオブジェクトを手で消した・置き場の障害・保存先の移し替えの失敗。アプリは消さない | 添付・版の行は直さない（追記専用）。バックアップなどから、**同じ保存キー**でオブジェクトを戻し、本文の SHA-256 が記録の `sha256` と一致することを確かめる。保存キーは読むだけの SQL で引く（画面にも窓口にも出さない） |
| 置き場にファイルがあり、予約の行が無い | DB からは見えない | 署名つきの送り先は予約の追記の後にしか作らないので、通常は起きない。起きたら手作業の混入などを疑う | 置き場のオブジェクトを手で消さない。調査は読むだけの SQL と置き場の一覧で行い、必要なら新しい書類として保存し直す |

「続きから保存」では、利用者が取引日・金額・取引先を入れ直す。この画面で送れなかった場合はファイルと入力を覚えているので引き継ぐが、頁を読み直した後は忘れる（ファイルは選び直すか、置き場に保存済みなら不要）。**差し替えの関係は予約の行に残っているので、読み直した後の再開でも保たれる**。確定は予約の差し替え元を版1へ写し、確定の窓口は差し替え元を本文で受けない（頁の状態に左右されない）。種類の検査に通らず新しい予約で保存し直す時は、止まった予約が持つ差し替え元を新しい予約に付け直す。

調べ方（読むだけ。本番では書かない）:

```sql
-- 保存が終わっていない予約（添付に結ばれていない物）。期限切れも含む
select r.id, r.purchase_order_id, r.kind, r.original_file_name, r.replaces_attachment_id, r.created_at, r.expires_at, r.expires_at < now() as expired
from public.purchase_order_attachment_reservations r
where not exists (select 1 from public.purchase_order_attachments a where a.reservation_id = r.id)
order by r.created_at;
```

期限切れの予約は、行を消さない・変えない（追記専用の表）。確認が済んだ印を付ける仕組みも作らない。確定するか、そのまま残す。

## 3. `sha256_source` の意味

添付の `sha256` は、置き場から読み戻した本文の SHA-256 で、`sha256_source` はその出どころを示す。

| 値 | 意味 |
| --- | --- |
| `browser` | ブラウザが送る前に計算した SHA-256 が、サーバーが読み戻した本文のハッシュと一致した。送ったファイルが改ざんや欠けなく置かれたことの確認になる |
| `server` | ページを読み直した後などでファイルが手元に無く、ブラウザのハッシュ無しで確定した。サーバーが置き場から読み戻した本文のハッシュを記録した。置かれたファイルが利用者の手元のファイルと同じかは、この確定では確かめていない |

どちらも、確定した後のファイルが記録のハッシュと一致するかを、後から再計算して確かめる材料になる。

## 4. 閲覧・ダウンロード・印刷

原本は窓口が60秒だけ使える署名つきリンクを作って返し、画面が新しいタブ（表示・印刷）か保存（ダウンロード）で開く。印刷は、開いたタブのブラウザの印刷で行う。リンクは応答にだけ載せ、監査・ログ・画面の文には出さない。調査でログを見る時も、リンクや保存キーは出力に無い（出ていたら不具合として扱う）。
