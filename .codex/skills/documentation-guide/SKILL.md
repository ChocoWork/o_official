# ドキュメント作成ガイド

本スキルは、リポジトリ内の Markdown ドキュメントを作成・更新する際に従うべきルールを定義する。6〜12 は、要求からコード・テストまでをたどれるようにする書式の正本（設計: `docs/superpowers/specs/2026-10-24-traceability-design.md`）。

## 適用範囲

- `docs/` 配下の全ドキュメント
- `README.md`
- `src/` のコードの TSDoc（9）と、`tests/`・`e2e/` のテスト名（10）

## ルール

### 1. プロフェッショナルなフォーマット

- 絵文字は **原則使用禁止** とする
- 例外: どうしても注意を引く必要がある箇所（重大な警告、破壊的変更など）に限り、最小限の使用を許可する
- 装飾目的での絵文字（見出しの先頭、一覧のアイコンなど）は禁止

### 2. 概要セクションの必須化

- 全てのドキュメントの先頭に **「概要」セクション** を設けること
- 概要セクションを読むだけで、ドキュメント全体の内容を大まかに把握できるようにすること
- 大量のドキュメントは人間にとって負荷が高い。概要セクションで読者が必要な箇所を素早く特定できるようにする

**構成例:**

```markdown
# ドキュメントタイトル

> メタ情報（対象システム、関連ドキュメントへのリンクなど）

---

## 概要

このドキュメントは〜を定義する。

### 主要なポイント（表や箇条書きで簡潔に）

| 項目 | 内容 |
|------|------|
| ... | ... |

---

## 1. 詳細セクション ...
```

### 3. 図表は Mermaid で記述

- フローチャート、シーケンス図、依存関係図などの図表は **Mermaid** で記述すること
- AA（アスキーアート）による図表記は禁止
- ディレクトリツリー構造（`├──` 等）はコードブロックのままでよい（Mermaid 化不要）

**使い分け:**

| 内容 | 記法 |
|------|------|
| フローチャート | `flowchart TD` / `flowchart LR` |
| シーケンス図 | `sequenceDiagram` |
| 依存関係・構成図 | `graph LR` / `graph TD` |
| クラス図 | `classDiagram` |
| ディレクトリツリー | コードブロック（` ``` `）|

### 4. 簡潔さの重視

- 冗長な説明は避け、要点を明確に記述すること
- 同じ情報を異なる形式で繰り返さない
- 表形式で整理できる情報は表を使う
- 長文の段落よりも箇条書きや表を優先する

### 5. 構造化

- 見出しレベルは `#`（H1）から `####`（H4）まで使用可能。H5 以下は使用しない
- 関連ドキュメントへのリンクは相対パスで記述する
- コードサンプルには適切な言語指定を付ける（` ```csharp `, ` ```mermaid ` 等）

### 6. 文書の種類と最小構成

正本の文書は次の形で書く（`docs/README.md` の「共通フォーマット」と同じ）。対象がない節は省略できるが、空の見出しや根拠のない「実装済み」は置かない。

1. `#` 文書名。直後に状態、確認日、対象、必要なら基準コミットを書く
2. `## 概要`。目的、対象範囲、読み手が得る結論を短く書く
3. `## 範囲と根拠`。対応する ID、対象コード、関連文書、調査時点と未確認の範囲を書く
4. 本文。図は Mermaid とし、図の境界、矢印の意味、例外を文章で補う
5. `## 未確認事項`。実測していない本番の設定や未定の契約を書く

| 文書の種類 | 本文の最小構成 | 置き場 |
| --- | --- | --- |
| 企画・コンテキスト | 目的、利用者・外部システム、境界、前提・制約、成功指標 | `docs/01_Planning/` |
| 要件・ユースケース | 安定 ID、出所、利用者と目的、事前条件、通常・代替フロー、受け入れ／検証方法 | `docs/02_Requirements/` |
| 要件（範囲内の領域） | 要求・要件・受け入れ条件・セキュリティ要件・派生要件の項目（7 の形） | `docs/02_Requirements/areas/<area>.md` |
| 基本設計 | 品質目標、制約、境界、主要構成、データと API の契約、重要な設計判断、リスク | `docs/03_BasicDesign/` |
| 構造設計（範囲内の領域） | 構成・画面・画面遷移・状態遷移・API・データの項目（7 の形） | `docs/03_BasicDesign/areas/<area>.md` |
| 設計判断（ADR） | 12 の ADR の型。1つの判断を1つのファイルに書く | `docs/03_BasicDesign/decisions/ADR-NNNN-<slug>.md` |
| 詳細設計 | 対応する ID、入出力、正常・異常フロー、状態・永続化、認証認可、テスト観点。範囲内の頁は `DD-` の項目（7 の形） | `docs/04_DetailDesign/` |
| 脅威 | 12 の脅威の型 | `docs/05_Quality/security/threats/<area>.md` |
| テスト仕様 | 対象の ID、レベル・環境、事前条件、入力・手順、期待結果、実行結果と証跡の参照 | `docs/05_Quality/tests/` |
| レビュー記録 | 対象のリビジョンと範囲、観点、指摘 ID・根拠・重大度・状態、再確認日 | `docs/05_Quality/reviews/` |
| 生成物 | スクリプトが作る。手で直さない（手書きの節・列だけは直してよい。11 を参照） | `docs/05_Quality/reports/trace-matrix.md`・`test-gaps.md`・`unused-code.md` |
| 運用手順 | 発動条件、影響、担当、手順、成功確認、ロールバック、記録・連絡先の管理場所 | `docs/06_Operations/` |

**範囲:** `scripts/trace/scope.json` に挙がった領域の文書・コード・テストが検査の範囲。範囲外は今は検査しない。

- 範囲内の ID の定義は、範囲内の文書（`areas/`・`decisions/`・`threats/`・挙がった詳細設計の頁）だけとみなす。`requirements.md` の写し元の行は定義に数えない
- `requirements.md` から写した項目には「旧所在」を書く。`requirements.md` の行は今は消さない（G-1 が落ち着いてから目次に置き換える）
- 範囲内と範囲外にまたがる行は丸ごと写し、範囲外の上位には `（範囲外）` の印を付ける（7）
- 文書を範囲に入れると、その中の `###`・`####` の見出しが全部読まれる。入れる前に 7 の形に直す

### 7. 項目の書き方

1つの項目は、1つの見出しと、その直後の属性の表で書く。検査のスクリプトはこの形だけを読む。

```markdown
### DD-NEWS-003 公開済みニュースの一覧の取得

| 属性 | 値 |
| --- | --- |
| 上位 | API-NEWS-002、SEC-NEWS-001 |
| 根拠 | 下書きを外へ出さない（SEC-NEWS-001）。並びは公開日の新しい順（FR-NEWS-ALL-001-AC-01） |
| 状態 | 推定 |
| 確かめ方 | 単体テスト |
| 出どころ | 実装から推定 |
| 旧番号 | IMPL-NEWS-LIST-001 |

本文（入出力・正常・異常・認可・永続化）。
```

**見出し:**

- `###` か `####` で書き、最初の語を ID、半角の空白を挟んで題を書く
- ID を `` ` ``・`**` で囲まない。ID の直後に `:`・`、` を付けない（`### DD-NEWS-003:` は ID として読まれない）
- 属性の表は見出しの直後に置く（間に挟めるのは空行だけ）。間に文を入れると属性が読まれない
- 1つの ID は1か所でだけ定義する（`duplicate-id`）
- 範囲内の文書では、最初の語が ID に似た見出しは全部読まれる。形の合う ID は項目として全部の検査を受け、形の合わない ID に表が続くと `bad-id` で落ちる。古い見出しは範囲に入れる時に直す（例: `### FREQ-232` は項目として読まれ属性が無ければ落ちる。`### R-01`・`### FREQ-AC-01-01-01` は `bad-id`）
- 「背景」「本文」など ID でない見出しは、`####` でも自由に使ってよい

**属性:**

| 属性 | 書く項目 | 中身 |
| --- | --- | --- |
| 上位 | 要求（`FREQ-NN`・`SR-`）・`THR-`・`DRV-` を除く全部（必須） | 上の段の ID。複数は `、` で区切る。範囲外の ID は直後に `（範囲外）` を付ける（例: `SEC-012（範囲外）`）。`（範囲外）` 付きの ID は、範囲内に定義があるか、範囲外の文書に現れていなければ落ちる。読み込んだ領域の中に定義のある `（範囲外）` 付きの ID は、道具が範囲内の上位として扱う（影響範囲・たどりが領域をまたぐ）ので、定義が範囲内に入ったら印を外す。範囲外の文書とは `docs/**/*.md` から、範囲内の文書・`graphify-out`・`docs/superpowers/**`・`docs/05_Quality/reports/**` を除いた物。範囲内の文書の本文に ID を書いても、知られた ID にはならない |
| 根拠 | 全部（必須） | なぜそうなっているか。上位の ID や出どころを添える |
| 状態 | 全部（必須） | `現行`・`推定`・`廃止` のどれか1つ（ほかの字は空とみなす） |
| 確かめ方 | 要件・設計 | E2E・結合テスト・単体テスト・レビューなど |
| 出どころ | 全部 | 過去の仕様のパス、ユーザーの発言、ブランド文書、法令。実装から起こした時は「実装から推定」 |
| 優先度 | 要件 | 元の文書の値（`MUST`・`SHOULD` など）。ISO/IEC/IEEE 29148 に合わせて持たせる |
| 旧番号 | 番号を振り替えた・引き継いだ項目 | 元の ID（例: 重複を振り替えた元の `FREQ-`、詳細設計の古い `IMPL-<page>-NNN`） |
| 旧所在 | 別の文書から写した項目 | 元の文書と節（例: `requirements.md` の「ニュース」節） |

**根拠の禁止:** 根拠を句読点と空白で区切った全部が「仕様のため」「要件のため」「仕様どおり」「必要なため」のどれかなら、根拠が無いとみなして落とす（`missing-rationale`）。決まり文句を言い換えただけの根拠も書かない。上位と中身が食い違う形だけのつなぎも不可（検査は中身の一致を見ないので、書く人が上位の本文と照らす）。

**状態:** 実装から起こした内容と、ユーザーの確認を受けていない内容は「推定」にする。ユーザーが確認したら「現行」にする。消した項目は「廃止」で残し、番号を使い回さない。廃止の項目は下位の検査を受けず、廃止の項目を指すと `retired-reference` で落ちる。

**上位に書ける種類と、下に要るもの:**

| 項目 | 上位に書ける種類 | 下に要るもの |
| --- | --- | --- |
| 要求 `FREQ-NN`・`SR-` | なし | 要件 |
| 要件 `FREQ-NN-REQ-NN`・`FR-`・`NFR-` | 要求 | 受け入れ条件 |
| 受け入れ条件 `-AC-NN` | 要件・`SEC-` | E2E のテスト |
| 脅威 `THR-` | なし | `SEC-` |
| セキュリティ要件 `SEC-` | `THR-` | 受け入れ条件・構造設計・`DD-` のどれか |
| 派生要件 `DRV-` | なし（理由は根拠に書く） | 構造設計 |
| 設計判断 `ADR-` | 要件・`SEC-`・`DRV-` | 構造設計 |
| 構造設計 `ARC-`・`SCR-`・`FLOW-`・`STATE-`・`API-`・`DATA-` | 要件・`SEC-`・`DRV-`・`ADR-`（要件・`SEC-`・`DRV-` のどれか1つは必ず入れる。`ADR-` だけでは足りない） | 結合テストと `DD-` |
| 詳細設計 `DD-` | 構造設計・`SEC-` | 単体テストと、`@design` で指すコードの単位 |
| 実装 `IMPL-` | — | 文書の見出しにしない。コードの TSDoc（9）に書く |

下の段は上の段の ID を書く。逆の向き（上から下）はスクリプトが作るので、上の項目に下の ID を書き足さない。

### 8. ID の体系

| 段 | ID | 例 | 上の段 | 置き場 |
| --- | --- | --- | --- | --- |
| 要求 | 既存 `FREQ-NN`、新規 `SR-<AREA>-NNN` | `FREQ-31`、`SR-NEWS-001` | なし（出どころ: ユーザーの発言・`stakeholder-requirements.md`・ブランド文書・法令） | `docs/02_Requirements/areas/<area>.md` |
| 脅威 | `THR-<AREA>-NNN` | `THR-NEWS-001` | 守るもの（資産） | `docs/05_Quality/security/threats/<area>.md` |
| 要件 | 既存 `FREQ-NN-REQ-NN`・`FR-<AREA>-NNN`・`NFR-…` | `FR-NEWS-ALL-001` | 要求 | 要件のファイル |
| 受け入れ条件 | 既存 `FREQ-NN-AC-NN`、新規 `<要件ID>-AC-NN` | `FREQ-31-AC-01`、`FR-NEWS-ALL-001-AC-01` | 要件 | 要件のファイル |
| セキュリティ要件 | 既存 `SEC-NNN`、新規 `SEC-<AREA>-NNN` | `SEC-NEWS-001` | `THR-`（中身は ASVS の項目） | 要件のファイル |
| 派生要件 | `DRV-<AREA>-NNN` | `DRV-NEWS-001` | なし。理由が必須 | 要件のファイル |
| 設計判断 | `ADR-NNNN`（4桁） | `ADR-0001` | 要件・セキュリティ要件・派生要件 | `docs/03_BasicDesign/decisions/ADR-NNNN-<slug>.md` |
| 構造設計 | `ARC-`（構成）・`SCR-`（画面）・`FLOW-`（画面遷移）・`STATE-`（状態遷移）・`API-`・`DATA-` に `<AREA>-NNN` を続ける | `API-NEWS-002` | 要件・セキュリティ要件・派生要件・ADR | `docs/03_BasicDesign/areas/<area>.md` |
| 詳細設計 | `DD-<AREA>-NNN` | `DD-NEWS-003` | 構造設計 | `docs/04_DetailDesign/pages/` の範囲内の頁 |
| 実装 | `IMPL-<AREA>-NNN` | `IMPL-NEWS-101` | `DD-` | コードの TSDoc |
| E2E | テスト名の先頭の受け入れ条件 ID | `FREQ-31-AC-01` | 受け入れ条件 | `e2e/` |
| 結合テスト | テスト名の先頭の構造設計 ID | `API-NEWS-002` | 構造設計 | `tests/integration/` |
| 単体テスト | テスト名の先頭の詳細設計 ID | `DD-NEWS-003` | 詳細設計 | `tests/unit/` |

- 既にある `FREQ-`・`FR-`・`NFR-`・`SEC-NNN` は番号を変えない
- 範囲（`scripts/trace/scope.json`）に入っている領域では、新しい `FREQ-` は振らない（G-1 が同じ `requirements.md` に `FREQ-` を足していて、番号がぶつかるため）。新しい要求は `SR-<AREA>-NNN` で起こし、要件は領域のファイルに書く。範囲に入っていない領域は、今までどおり CLAUDE.md の「要求管理ルール」（`requirements.md` に次の `FREQ-` を足す）に従う
- 範囲内で重なった `FREQ-` の番号は、2つ目以降を `SR-<AREA>-NNN` に振り替え、元の番号を「旧番号」に残す
- `FR-`・`NFR-` は要件として扱う。受け入れ条件を持たない要件には `<要件ID>-AC-NN` を新しく起こす
- 上の要求が見つからない要件は、`stakeholder-requirements.md` やブランド文書から `SR-` を起こしてつなぐ。起こした `SR-` は「推定」にする
- 派生要件 `DRV-`（要求の外で足したもの）は、根拠に足した理由を書き、下に構造設計を必ず持たせる
- 詳細設計の頁に既にある `IMPL-<page>-NNN`（例: `IMPL-NEWS-LIST-001`）の行は、新しい `DD-` の項目の「旧番号」に移す
- 新しい `IMPL-<AREA>-NNN` は、その領域に既にある `IMPL-<AREA>-NNN` の最大より大きい、きりのよい番号から振る（文字の上で混ざらないように。NEWS は既存の最大が `IMPL-NEWS-003` なので 101 から）
- `<AREA>` は領域の英字名（HOME・NEWS・LOOK・ABOUT・STOCKIST・SEARCH・AUTH・PRIVACY・ADMIN など）。英大文字で始まる語を `-` でつなぐ（例: `NEWS-ALL`）
- 番号は領域ごとの連番で3桁にそろえる（ADR は4桁）。振ったら変えない。消した項目の番号は使い回さない（「廃止」で残す）

### 9. コードのコメント

範囲内のコードの「まとまった単位」ごとに、TSDoc で `@impl` と `@design` と「なぜ」を書く。単位は次のとおり（検査のスクリプトがこの決まりで単位を数える）。

| 単位 | 単位になるもの | 例 | コメントの置き場 |
| --- | --- | --- | --- |
| ファイル | `.tsx` の全部と、`src/app/` の `page`・`layout`・`route`・`loading`・`error`・`not-found`（`.ts` も含む） | `src/app/api/news/route.ts`、`src/app/news/page.tsx`、`src/features/news/components/PublicNewsGrid.tsx` | ファイルの先頭。`'use client'`・`'use server'`・`import` より前に、`@packageDocumentation` を含む TSDoc を置く |
| 関数・クラス | 上のほかの `.ts` で、`export` を付けて書いた関数宣言・関数を入れた `const`（矢印関数・関数式）・クラスと、`export default` の関数 | `src/features/news/services/public.ts` の `getPublishedNews()`、`src/app/actions/news.ts` の Server Action | その文の直前の TSDoc |

- `'use server'` のファイルでは、export された関数の1つ1つが単位（クラスは数えない）
- 単位にならないもの: `.d.ts`、型だけのファイル、export されない関数、`.tsx` の中の関数（ファイルの単位に含める）、後から出す `export { f }`、ほかのファイルからの `export … from`
- `'use client'`・`'use server'` の行自体は動かさない。コメントは文ではないので、その前に置いても指示は効く

ファイルの単位:

```tsx
/**
 * 公開済みのニュースを格子に並べる部品（src/features/news/components/PublicNewsGrid.tsx）。
 *
 * @packageDocumentation
 * @impl IMPL-NEWS-101
 * @design DD-NEWS-001
 * @remarks <利用者の端末で動かす理由など、読んでも分からない「なぜ」だけを書く>。
 */
'use client';
```

関数の単位:

```ts
/**
 * 公開済みのニュースだけを公開日の新しい順に返す。
 *
 * @impl IMPL-NEWS-103
 * @design DD-NEWS-003
 * @remarks 下書きを外へ出さないため、公開の印は DB 側で絞る（SEC-NEWS-001）。
 */
export async function getPublishedNews(options?: GetPublishedNewsOptions): Promise<PublicNewsArticle[]> { … }
```

- `@impl` と `@design` は必須。`@impl` は1つで、範囲内で同じ `IMPL-` を2回使わない（`missing-impl`・`duplicate-impl`）
- `@design` はちょうど1つで、範囲内に定義のある `DD-` を指す（`bad-design-link`）。1つの `IMPL-` は1つの `DD-` にだけつなぐ。1つの `DD-` には複数の `IMPL-` がつながってよい
- `@remarks` には「なぜ」だけを書く。読めば分かる「何を」は書かない
- 関数の中の行コメントは、読んだだけでは分からない理由がある所（セキュリティの判断・外部仕様の癖・順番が大事な所）だけに書く
- コードにはテストの場所を書かない（逆の向きはスクリプトが作る）
- コメントを足す作業では動きを変えない。コメント以外の変更は入れない
- ソースを文字として読む試験があるので、コメントを足す前に `tests/` をそのファイルの名前で検索して確かめる
- 共有部品（`lib/auth/*`・`lib/csrf*`・`lib/audit.ts`・`lib/supabase/*`・`components/ui/*` など）にはコメントを入れない。つなぎ先は設計の文書の上位に `（範囲外）` 付きで書く

### 10. テストのつなぎ方

テスト名（`test()`・`it()` の最初の引数）の先頭に ID を書き、半角の空白を挟んで中身を書く。

```ts
test('FR-NEWS-ALL-001-AC-01 ニュースが公開日の新しい順に並ぶ', async ({ page }) => { … });
it('DD-NEWS-003 下書きのニュースを返さない', () => { … });
```

| テストの段 | 置き場 | 名前の先頭に書く ID |
| --- | --- | --- |
| E2E | `e2e/` | 受け入れ条件（`-AC-NN`） |
| 結合テスト | `tests/integration/`。画面・画面遷移（`SCR-`・`FLOW-`）は `tests/integration/ui/` に React Testing Library で画面単位に書く | 構造設計（`ARC-`・`SCR-`・`FLOW-`・`STATE-`・`API-`・`DATA-`） |
| 単体テスト | 上のほか（`tests/unit/`） | 詳細設計（`DD-`） |

- 段は置き場で決まる。段に合わない種類を書くと `wrong-test-level` で落ちる
- テストのファイルは、パスが `scope.json` の `tests`・`e2e` の型（glob）に合う時だけ範囲に入る（NEWS なら、単体テストは名前に `news`・`News` を含むか `news/` の下、結合テストは名前に小文字の `news` を含むか `news/` の下、E2E は `e2e/FR-NEWS-*.spec.ts`。`tests/integration/ui/NewsList.test.tsx` のような大文字始まりの名前は範囲外になる）。`tests/unit/`・`tests/integration/` の新しいファイルの名前は小文字のケバブ（例: `news-list.test.tsx`）にする。新しい E2E のファイルは今までどおり `e2e/FR-<AREA>-NNN-<kebab>.spec.ts` の名前にし（範囲の e2e の型に合わせるため）、mobile 390・tablet 768・desktop 1280 の3つの幅で試し、本番ビルドに対して流す
- 読むのは `test`・`it`（`.only`・`.skip`・`.todo`・`.fixme`・`.each` を含む）の名前だけ。`skip`・`todo`・`fixme` の試験は実行しないので、受け入れ条件・構造設計・詳細設計の「試験がある」に数えず、`test-gaps.md` の「飛ばしている試験」の節に出す（WONT の受け入れ条件のように飛ばしている物は `missing-child` に出て、基準に持つ）。`describe` の名前とファイルの名前はつなぎにならない。E2E のファイル名（`FR-NEWS-ALL-001-….spec.ts`）は変えず、テスト名に受け入れ条件の ID を書く（要件の ID ではなく）
- テンプレート文字列の名前は、先頭の ID を `${…}` にせず字で書く
- 範囲内のテストは全部、名前の先頭に ID が要る（`untagged-test`）。ID は範囲内に定義が要り（`unknown-test-id`）、廃止の項目を指さない
- 既にあるテストの名前に ID を付ける前に、範囲内の E2E を流して基準を取り、`npm run trace:compare-e2e` で前後を比べる。結果の JSON は PowerShell で `$env:PLAYWRIGHT_JSON_OUTPUT_NAME="$env:TEMP\x.json"; npx playwright test <パス> --reporter=json` のように作る（前と後で別の名前にする）
- つないだ時にテストが無ければ、その場で書き足す。E2E は CLAUDE.md の決まり（mobile 390・tablet 768・desktop 1280 の3つの幅、本番ビルド、手元の Supabase）に従う

### 11. 確かめ

範囲内の文書・コード・テストを変えたら、次を通す。

| コマンド | 確かめること |
| --- | --- |
| `npm run validate-trace`（`-- <AREA>` で領域を絞る） | 6〜10 の決まり。違反を `ファイル:行 [決まりの名前] 中身` で出す。既知の違反は `scripts/trace/baseline.json` に持ち（出力に「（既知）」と付く）、**基準より増えた違反が1つでもあれば**終了コード 1。直して基準から消す時と、承認した違反を足す時は `npm run validate-trace -- --update-baseline`（全領域だけ）。どのファイルにも当たらない `scope.json` の型は件数の警告が出る（一覧は `-- --list-unmatched`） |
| `npm run trace -- <ID かファイル>` | 上（要求まで）と下（テストまで）と、同じ `DD-` を共有する単位。変える前の影響範囲の分析に使う |
| `npm run trace:report` | 生成物 `docs/05_Quality/reports/trace-matrix.md`・`test-gaps.md`・`unused-code.md` を作り直す。生成物は全領域をまとめた1つの一覧なので、領域名を渡しても全領域を書く（1つの領域だけで書き直すと、ほかの領域の行が消える） |
| `npm run test:trace-coverage` | 範囲内の単体テスト（結合 `tests/integration/` 以外）を流し、範囲内のファイルの分岐の網羅を測り、届かない分岐を `test-gaps.md` の「届かない分岐」の節と突き合わせる（`scripts/trace/check-coverage.ts`）。節に無い届かない分岐と、節にあるのに今は届いている行があれば終了コード 1（「分岐の網羅の数には入らない」と書いた行は外す）。領域は環境変数 `TRACE_AREAS` にカンマ区切りで渡し、無ければ `scope.json` の全部。PowerShell では `$env:TRACE_AREAS='NEWS'; npm run test:trace-coverage`（`-- NEWS` の書き方は使えない） |
| `npm run trace:compare-e2e -- <前の JSON> <後の JSON>` | テスト名に ID を付ける前後の E2E の結果（Playwright の JSON）を、名前の対応で比べる |
| `npm run validate-docs` | Markdown の形、相対リンク、Mermaid の図 |

`validate-trace` の決まりの名前:

| 名前 | 落ちる時 |
| --- | --- |
| `duplicate-id` | 1つの ID が2か所以上で定義されている |
| `bad-id` | 最初の語が ID に似た見出しの形が合わず、属性の表が続く（表が続かない見出しは落とさない） |
| `missing-status` | 状態が空、または `現行`・`推定`・`廃止` 以外 |
| `missing-rationale` | 根拠が空、または決まり文句だけ |
| `missing-parent` | 上位が要る種類なのに上位が空 |
| `wrong-parent-kind` | 上位に書けない種類を書いた。構造設計の上位に要件・`SEC-`・`DRV-` が無い |
| `unknown-parent` | 上位の ID が範囲内に無い（`（範囲外）` 付きは、範囲内の文書にも、7 の「上位」の行で決めた範囲外の文書にも無い） |
| `missing-child` | 7 の表の「下に要るもの」が無い |
| `retired-reference` | 廃止の項目を指している |
| `missing-impl`・`duplicate-impl`・`multiple-impl` | 単位に `@impl` が無い・同じ `IMPL-` が2つある・1つの単位に `@impl` が複数ある |
| `bad-design-link` | `@design` が1つでない・`DD-` でない・範囲内に無い |
| `untagged-test`・`wrong-test-level`・`unknown-test-id` | テスト名の先頭に ID が無い・段に合わない・範囲内に無い |

- 生成物は手で直さない。手で書いてよいのは、`trace-matrix.md` の「食い違い」節、`test-gaps.md` の「届かない分岐」節、`unused-code.md` の「判断」の列だけ（作り直しても引き継がれる）
- 文書とコードが食い違ったら、どちらが正しいかを決めずに「食い違い」節に載せてユーザーに聞く
- テストで届かない分岐（型の上では起きない道など）は、理由を「届かない分岐」節に1件ずつ書く。書き足せるテストの逃がし先にしない。1行に1件、``- `src/…/file.ts:42` 理由。確認: 未`` の形で書く（`-` か `*` で始め、`ファイル:行` を書き、空白の後に理由）。この形に合わない行は警告が出て、作り直しの時に消える
- 使われていないコードは消さずに `unused-code.md` に載せる。判断はユーザーが書く。見つけ方は「参照なし」（どこからも import されない）、「試験だけが参照」（`tests/`・`e2e/`・`scripts/` からだけ import され、製品のコードからは使われない）、「要件につながらない」の3つ

### 12. 型

**設計判断（ADR）:** Nygard の ADR の形。1つの判断を1つのファイルに書く。

```markdown
# ADR-0001 <判断の題>

> 状態: 現行 | 確認日: 2026-10-24 | 対象: `src/…`

## 概要

<決めたことを1〜2文で>

### ADR-0001 <判断の題>

| 属性 | 値 |
| --- | --- |
| 上位 | FR-NEWS-ALL-001、SEC-NEWS-001 |
| 根拠 | <なぜこの判断が要ったか> |
| 状態 | 推定 |
| 出どころ | `docs/superpowers/specs/…md`、または「実装から推定」 |

#### 背景

<判断を迫った事情・制約>

#### 決定

<選んだ案>

#### 退けた案

| 案 | 退けた理由 |
| --- | --- |
| <案> | <理由> |

#### 結果

<良くなること・悪くなること・後で見直す条件>
```

- 状態は 7 と同じく `現行`・`推定`・`廃止`。別の ADR に置き換えた時は古い方を「廃止」にし、「結果」に置き換え先の ADR を書く
- ADR の下には、その判断に従う構造設計が要る（構造設計の上位に `ADR-` を書く）

**脅威:** 領域ごとのファイルに、脅威を1つずつ項目で書く。既にある `docs/05_Quality/reviews/security/` の指摘から起こす。

```markdown
### THR-NEWS-001 <脅威の題>

| 属性 | 値 |
| --- | --- |
| 守るもの | <資産。例: 公開前の下書きの記事> |
| 脅威 | <誰が何をするか> |
| 起こり方 | <入口と手順> |
| 影響 | <起きた時の害> |
| 対策 | SEC-NEWS-001 |
| ASVS | <OWASP ASVS 4.0.3 の項目番号> |
| 根拠 | <なぜこの脅威を考えるか。出どころの指摘 ID など> |
| 状態 | 推定 |
| 出どころ | `docs/05_Quality/reviews/security/…md` |
```

- 「対策」の欄は読み手のための写し。つながりは、セキュリティ要件 `SEC-` の上位に `THR-` を書いて作る
- `SEC-` は要件のファイルに 7 の形で書き、上位に `THR-`、中身に ASVS の項目番号を書く。`SEC-` の下には受け入れ条件・構造設計・`DD-` のどれかが要る
